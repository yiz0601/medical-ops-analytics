## 二、项目概况与建设目标回顾

### 2.1 项目概况

| 项 | 内容 |
| --- | --- |
| 建设定位 | 不替代 HIS/EMR/LIS 生产系统，作为其上的运营数据整合与分析层，形成"数据—分析—决策—验证"闭环 |
| 技术栈 | Python 3.11 + FastAPI · MySQL 8.0 · Vue 3 + ECharts 5 · Docker Compose + Nginx · LLM（NL2SQL） |
| 数仓分层 | ODS（贴源）→ DWD（明细/宽表）→ DWS（汇总）→ ADS（集市 + 指标结果），辅以 DIM 公共维表 |
| 数据时间窗 | 2025-04-01 ~ 2025-06-30（91 天） |
| 数据组织维度 | 10 个临床科室（EK/FC/GK/HN/HX/ICU/JZ/PW/SJ/XH），开放床位合计 177 张 |
| 指标规模 | 33 项（M01–M33），其中 30 项产出数值、3 项（M04/M05/M27）因数据源缺字段记 `NULL` + `PENDING` |
| 交付形态 | `docker compose` 一键启动 mysql / backend / frontend / nginx 四服务；开发态 `uvicorn` + `vite dev` 直接可跑 |

### 4.2 阶段二：多源数据采集与整合

| 项 | 内容 |
| --- | --- |

### 4.3 阶段三：数据仓库建模与指标计算

| 项 | 内容 |
| --- | --- |
| 关键任务 | T07 DIM/DWD 分层建模；T08 DWS/ADS 分层建模；T09 指标口径定义与指标计算校验 |

| 处理方式 | ① 采用 `dim_drg_group` 模拟分组（按 ICD-10 主诊断映射 10 个模拟组与 RW），全部病种类图表标注"模拟分组"，生产替换院方分组器而公式不变（ADR-04）；② 明确 K4：仅用于功能演示，不得输出科室绩效排序结论，页面加角标；③ 三口径在指标定义处显式声明来源表（M03/M13 取登记口径，M07/M15/M16 取流水口径，M19/M20 取财务口径），对账规则提示级不阻断（K1、K2） |

## 五、关键技术实践

### 5.1 三口径（登记/流水/财务）分离与显式标注

| 项 | 内容 |
| --- | --- |
| 问题背景 | 模拟数据中"登记口径"（就诊登记时的汇总费用）、"流水口径"（逐笔收费明细）、"财务口径"（财务日报导出）三条路径**互相不勾稽**：门诊登记口径次均 425.15 元，流水口径反算 2,992.28 元；财务口径收入 41,446,631.11 元与流水口径 44,260,283.80 元相差 −6.36%。若不显式区分，任何"收入 ÷ 次均费用 = 人次"的推导都会得出错误结论 |
| 方案 | ① 在指标定义层强制声明来源字段：M03/M13 取 S1.`fee_amount`、S2.`total_fee`（登记口径），M07/M15/M16 及 M17–M22 取 S3.`amount`（流水口径），M19/M20 默认取 S6 财务口径；② 禁止跨口径混算，接口提供口径参数与 `metric_version`；③ 对账差异以规则形式登记（`QR-REC` 系列行数对账 + 口径差异说明），差异阈值内判定通过、提示级不阻断；④ 前端图表以口径角标标注并保留"财务/流水"切换 |
| 效果 | 33 项指标全部可从《[指标口径手册](指标口径手册.md)》逐项回溯到字段；对账 10 项独立复算全部通过（最大误差 3.3e-05）；评审记录 R-03/R-04 明确确认药占比 30.00%、耗占比 10.00%、次均费用取登记口径 |

### 5.2 模板优先 NL2SQL 防口径漂移

| 项 | 内容 |
| --- | --- |
| 问题背景 | 若允许大模型自由生成 SQL，模型可能拼出"流水收入 ÷ 登记次均"这类跨口径查询，或对无数据源的指标编造数值；同时开放 SQL 生成意味着表结构暴露与注入风险 |
| 方案 | ① `backend/app/llm/nl2sql.py` 只做意图解析（指标编码 + 维度 + 时间粒度 + 过滤条件），SQL 由 `metric_def` 口径模板拼装；② 白名单校验（仅 `ads_*`/`dws_*`/`dim_*`、只读、强制 limit）；③ 数值答案必须来自 ADS 结果集，缺数据源的指标（M04/M05/M27）返回"数据源待补充"而非猜测；④ 提供离线规则引擎，在无外部模型时同样可评测 |
| 效果 | 50 条评测集（8 个主题 × 3 种粒度，含 easy/medium/hard 三档难度）离线规则引擎 **100% 命中**（评分规则：指标编码 + 维度值 + 粒度三项全对），显著高于 85% 验收阈值；注入型问题被拒绝，隐私字段不出网 |

### 5.3 DDL 由表结构代码自动生成防漂移

| 项 | 内容 |
| --- | --- |
| 问题背景 | 表结构存在两份"事实"（Python 表定义与 `sql/` 下手写脚本）时必然漂移：改一列忘一处，容器初始化的库与代码运行的库不一致，表现为运行期列缺失错误 |
| 方案 | `backend/etl/jobs/export_ddl.py` 以 `backend/etl/config/{dim,ods,dwd,mart}_schema.py` 为**单一事实来源**，用 SQLAlchemy MySQL 方言渲染 `CREATE TABLE`，自动生成 `sql/{dim,ods,dwd,dws,ads}/` 下五层建表脚本，维表初始化数据由 `dim_seed.py` 渲染为 INSERT；容器首次启动通过 `sql/00_init_all.sql` 用 `SOURCE` 按 dim → ods → dwd → dws → ads → optimize 顺序执行 |
| 效果 | 代码表结构 = 数据库表结构，`sql/` 下 9 个脚本由脚本生成而非手写；新增 `sql/optimize/optimize_indexes.sql` 幂等建索引；本阶段末新增列引起的运行期失败（4.7 节）反向印证了"缺统一迁移入口"的风险边界——生成能力已具备，但开发库仍需人工重建或补迁移脚本 |

### 5.4 幂等装载与区间回刷

| 项 | 内容 |
| --- | --- |
| 问题背景 | ETL 重跑若采用追加写，行数会翻倍；口径变更或数据补录后需要按历史区间重算，若无回刷工具只能整库重建 |
| 方案 | ① 所有 ODS/DWD/DWS/ADS 写入按 `etl_batch_id` **先删后插**，同一批次重复执行行数不变；② `backend/etl/jobs/backfill.py` 提供 `backfill(start_date, end_date)`，按区间重跑 DWD → 宽表 → DWS/集市 → 指标加工链并返回各层影响行数；③ ADS 指标表以"指标编码 + 维度值 + 粒度 + 统计日期"为唯一键，重跑覆盖而非累积 |
| 效果 | 试运行 120 次任务累计执行中，ODS/DWD/DWS/ADS 行数始终等于基线（9,000/1,500/44,078/1,500/2,934/910），未出现重复装载；`backfill.py` 使"口径变更后按区间回刷"成为可执行命令而非人工操作 |

### 5.5 数据权限行级隔离

| 项 | 内容 |
| --- | --- |
| 问题背景 | 科室用户（如 `dept_hn` 呼吸内科）只应看到本科室数据，若由 11 个路由模块各自写过滤条件，必然出现漏判；越权一旦发生属于隐私与合规事故 |
| 方案 | ① 认证与用户上下文集中在 `backend/app/core/deps.py`：`get_current_user()` 解析 JWT 并回查用户，`require_role()` 校验角色，`apply_data_scope(stmt, user)` 对查询语句统一追加科室过滤；② 接口内部**禁止**手写 `dept_code` 过滤，代码评审列为必查项与红线；③ 越权返回 40301/40302 并写审计；④ 登录、查询、导出、触发任务四类操作落 `sys_audit_log` |
| 效果 | `dept_hn` 查询自动限定 `dim_value=HN`，无法看到全院汇总行；越权用例（构造他科 `dept_code`、越权导出）在 `backend/tests/test_security.py` 中全量覆盖并全部拦截 |

### 5.6 前端 ECharts 按需引入与分包

| 项 | 内容 |
| --- | --- |
| 问题背景 | ECharts 全量引入会使首包体积逼近 1 MB，叠加 Vue 生态后首屏加载与构建告警都不可接受；同时随机型增加组件会导致图表代码重复 |
| 方案 | ① `frontend/src/components/charts/useChart.js` 只从 `echarts/core` 注册实际使用的 `BarChart/LineChart/PieChart/HeatmapChart` 与 `CanvasRenderer`；② `frontend/vite.config.js` 配置 `manualChunks`，将 `echarts` 与 `vue` 生态拆为独立 chunk，并设 `chunkSizeWarningLimit: 1200`；③ 5 个通用组件统一 props（标题/数据/加载/空态/角标），页面侧用 `ThemeBoard` 组合模板拼装，避免 12 套重复实现；④ 路由全部懒加载，`beforeEach` 统一守卫登录态与角色 |
| 效果 | `vite build` 2.54 s 成功构建，产物 echarts 583.98 KB（gzip 195.52 KB）、vue 102.46 KB（gzip 39.85 KB）、index 71.72 KB（gzip 27.31 KB），无体积超限告警；`frontend/dist/` 已产出可直接由 Nginx 托管的静态资源 |

### 5.7 用自动化测试守住"文档表格被批量替换清空"这类回归

| 项 | 内容 |
| --- | --- |
| 问题背景 | 项目文档以表格承载绝大多数基线与口径。此前一次**批量文本替换操作**把整份文档的表格竖线删空，Markdown 表格退化为普通文本，评审时才发现，属于"人工难以逐页复核、机器可秒级发现"的典型事故 |
| 方案 | 新增 `backend/tests/test_docs_integrity.py`，对 `docs/` 下 10 份基线文档与根目录 `README.md`/`CONTRIBUTING.md` 做四类参数化断言：① 文件存在且非空；② 竖线数量不低于下限（`MIN_PIPES=30`，用于发现"表格被清空"）；③ 每个表格区块列数一致（正确处理 `\|` 转义竖线、跳过代码围栏内伪表格）；④ 文档内相对链接可解析。同一批次配合 `backend/tests/test_4_3_docs.py` 校验 OpenAPI 路由覆盖与统一响应外壳 |
| 效果 | 任何一次误伤表格或断链的批量修改都会在 pytest 中立即失败（当前 120 项用例全通过）；文档一致性与接口契约从"人工抽查"变为"每次提交自动校验"，`--cov-fail-under=80` 同时约束覆盖率不得回退（实测 88.00%） |

## 六、经验教训

### 6.1 技术经验

| 序号 | 教训 | 具体表现 | 后续约束 |
| --- | --- | --- | --- |
| T-1 | **数据特征必须在文档中如实披露，不能靠"清洗"掩盖** | 模拟数据存在双口径不勾稽（K1）、财务与流水差异 6.36%（K2）、无 DRG 分组器（K3）、科室业务量均匀（K4）、当日出入院 17 例（K5）、6/30 窗口截断出院 190 例（K6）、手术费近乎全覆盖 98.73%（K7）、缺预约/退号/死亡字段（K8）。若把窗口截断当脏数据清洗掉，月度指标会失真 | 8 条特征逐条写入《[指标口径手册](指标口径手册.md)》第 6 章，并要求每条特征都有对应的页面角标或注释；质量规则对已知特征降级为 WARN 而非 BLOCK |
| T-2 | **开发库表结构不做自动迁移，会在运行期以"列不存在"的形式爆炸** | 试运行中 `clean_dwd` 连续 2 次失败：`table dwd_charge_detail has no column named dept_parent_code`，直接导致整体任务成功率 98.33% 而非 100%，并登记为 P0 缺陷 | 开发态统一用建表脚本重建库；生产态只认 `sql/` 全量 DDL 初始化；新增列必须同时提供迁移脚本，纳入"交付物核对表"检查项 |
| T-3 | **口径必须"声明来源"而不只是"写出公式"** | 早期若只写公式，实现时容易用流水收入 ÷ 登记次均反推人次，得出全盘失真的数值 | `metric_def` 强制包含 `source_tables`；代码评审设"口径一致性"必查项；断言中加入量纲校验（人次必须严格相等、金额 ±0.01 元） |
| T-4 | **自动化文本改写是高危操作，需要测试护栏** | 批量替换曾把整份文档的表格竖线删空，Markdown 渲染列错位，人工评审才发现 | 建立 `test_docs_integrity.py` 四类断言；批量改写后必须跑一次 pytest 再提交（对应 5.7 节） |
| T-5 | **模拟数据的"均匀性"会误导分析结论** | 10 个科室每科 900 门诊 / 150 出院，各病组次均费用 15,333.89–16,319.92 元、ALOS 8.40–10.31 天，导致费用与时间消耗指数均约 0.9174，"看起来科室效率完全一致" | 明确 K4 仅用于功能演示，禁止输出科室绩效排序结论；报告与页面均注明"模拟数据特征"，避免把演示数据当业务发现 |

### 6.2 管理经验

| 序号 | 教训 | 具体表现 | 后续约束 |
| --- | --- | --- | --- |
| M-1 | **先"数对"再"好用"，阶段顺序不可倒置** | 项目按"数据链路（自下而上）+ 应用链路（自上而下）"切分：阶段二、三锁定口径与质量，阶段四、五、六只取数不计算。若前端先行，错误口径会被放大到每个图表 | 保持 M1–M7 阶段门禁：前一阶段未通过（或带条件通过未闭环）不得进入下一阶段 |
| M-2 | **缺字段的指标要在最早阶段冻结降级策略** | M04/M05/M27/M28/M29 若到开发中期才发现不可实现，会造成接口、前端、文档三处返工 | 阶段一即写入降级策略（`NULL` + `PENDING` + "数据源待补充"标注），并作为验收断言的一部分；口径评审记录 R-09 明确"不产出数值" |
| M-3 | **文档数值纪律必须唯一来源** | 基线值若在不同文档各写一份，必然出现"看着都对、数字不同"的争议 | 基线唯一来源为《[指标口径手册](指标口径手册.md)》第 5 章；实测值只能来自执行记录并注明来源文件；本报告 1.4 节对 4 处表述差异做了显式披露而非"对齐美化" |
