## 一、培养定位

### 1.1 项目式培养理念（真数据、真链路、真交付）

本项目的培养方式不做"练习题堆砌"，而是把学员放进一个可运行、可验收、可答辩的完整工程里，做三件真事。

| 理念 | 含义 | 在本项目中的落地 | 学员拿得到的证据 |
| --- | --- | --- | --- |
| **真数据** | 数据不裁剪、不美化，含真实医院数据的"脏"与"不合逻辑" | 统一时间窗 2025-04-01 至 2025-06-30（91 天）、10 个临床科室（合计开放床位 177 张）；6 个 CSV 源文件：门诊 9,000 行、住院 1,500 行、收费明细 44,078 行、病历 1,500 行、检验 2,934 行、财务日报 910 行，合计 59,922 行 | 源文件与入库行数核对表；`data/README.md` 特征说明与处理约定 |
| **真链路** | 从源文件到管理者手机上看板的那条链路，每一段都要自己打通 | HIS/EMR/LIS/财务/文件 5 类数据源 → ODS → DWD → DWS → ADS → FastAPI `/api/v1` → Vue3 + ECharts 看板 → 大模型 NL2SQL | 端到端演示（ETL 批次号 → ADS 指标 → 接口响应 → 页面图表），全链路可追溯 |
| **真交付** | 交付物按工程标准验收，不是"交作业" | 10 份项目文档 + 4 类代码 + `docker compose up` 一键三容器部署 + 3 套看板 + 33 项指标 + NL2SQL 问数 | 可运行系统、验收报告、答辩录屏、岗位作品集素材 |

**四条不可妥协的原则（贯穿全部阶段，也是评分红线）**

1. **口径唯一**：指标只在 ADS 层实现一次，公式必须引用《指标口径手册》的 `M01`~`M33` 编号；代码中私自定义口径即判定不合格。
2. **基线可回放**：每一项可计算指标都必须与手册第 5 章基线值比对，金额容差 ±0.01 元、比率容差 ±0.01 个百分点，人次/床日必须完全相等。
3. **来源显式**：登记口径（`fee_amount` / `total_fee`）、流水口径（`his_charge.amount`）、财务口径（`finance_excel.revenue`）三条路径必须逐项标注，禁止跨口径混算。
4. **数据合规**：`data/` 全部为模拟数据，仅用于开发、演示与验收；姓名、证件号、手机号自 DWD 层起强制脱敏；明细行与隐私字段禁止送入外部大模型。

## 三、能力模型与能力矩阵

### 3.1 能力项清单（C01–C18）

> 每项均给出"合格 / 良好 / 优秀"三档达标标准；"合格"是最低交付线，"优秀"须有可复现证据。评分细则见 6.2 节。

**C01 医疗业务理解与运营指标体系认知**
- 能力描述：能说清门诊、住院、收入、病种、资源效率五条业务主线，能解释指标为什么这样定义、数据从哪里来。
- 达标标准：合格 = 正确解释 ≥8 项指标的临床与管理含义，能对照 10 个科室说明业务关系（证据：阶段一评审记录 + 指标目录卡片）；良好 = 正确解释 ≥20 项，并能说明 M04 预约率、M05 退号率、M27 低风险组死亡率、M28 医师人均门诊人次、M29 床护比因模拟数据缺字段而无法计算的原因；优秀 = 能在评审中主动指出口径歧义（如"次均费用"与"收入合计"不可相乘反推人次）并形成书面口径问答条目 ≥5 条。

**C02 需求分析与技术文档表达**
- 能力描述：能把"想看运营数据"翻译成带编号、优先级、验收条件的功能需求，并产出结构完整的技术文档。
- 达标标准：合格 = 独立写出 ≥1 个模块的需求条目（含验收条件），格式与《需求规格说明书》一致；良好 = 需求条目可追踪到具体接口与页面，且能被测试用例覆盖；优秀 = 主导一次需求评审，闭环 ≥5 条评审意见并回填文档。

**C03 数据源接入与文件解析**
- 能力描述：能注册 5 类数据源（HIS / EMR / LIS / 财务 / 文件通道），解析 6 个 CSV 源文件并映射到 ODS 贴源表。
- 达标标准：合格 = 6 个 CSV（`data/mock_his/` 下 5 个 + `data/files/` 下 1 个）全部入库，行数与基线完全一致（9,000 / 1,500 / 44,078 / 1,500 / 2,934 / 910）；良好 = 实现模板校验与错误行反馈（`meta_file_upload` 记录 valid_rows / error_rows）；优秀 = 增量抽取（按 `fee_date`、`report_date`）可重复执行且结果幂等，并附抽取策略说明。

**C04 数据质量规则设计与质量校验**
- 能力描述：能设计完整性、唯一性、值域、波动率、跨源对账五类规则并落成可执行校验，产出批次质量报告。
- 达标标准：合格 = 落地 ≥8 条规则（须含主键唯一、必填非空、日期逻辑"出院 ≥ 入院"、金额非负）；良好 = 规则可配置入 `dq_rule`（BLOCK / WARN 分级），批次输出质量评分与问题明细；优秀 = 正确处置两条特殊对账规则：`QR-CHG-03` 在演示环境为提示级（因登记口径与流水口径独立生成），`QR-REC-01` 按财务口径 41,446,631.11 元与流水口径 44,260,283.80 元差异约 6.4% 在 ±10% 容差内判定通过，并在报告中书面说明理由。

**C05 ETL 任务开发与调度编排**
- 能力描述：能编写采集、清洗、汇总、指标四类 job，按依赖顺序编排调度，做到批次可追溯、失败可重试。
- 达标标准：合格 = 4 类 job 可手动执行成功，`etl_batch_id` / `etl_load_time` 正确写入；良好 = APScheduler 按 cron 触发 + 失败重试 + 运行日志落 `meta_task_run`（状态、耗时、行数）；优秀 = 按 `etl_batch_id` 幂等重跑与回刷不产生重复数据，并提供一次"故障重跑 → 数据恢复一致"的演示记录。

**C06 隐私脱敏与数据合规**
- 能力描述：能在 DWD 层起落实脱敏规则，明确 ODS 与 DWD 的访问边界，控制 AI 链路的数据出网范围。
- 达标标准：合格 = 姓名（`张**`）、身份证（保留前 6 后 4）、手机号（保留前 3 后 4）三个字段脱敏正确，可随机抽查验证；良好 = ODS 仅 DBA/ETL 账号可读的权限说明与实现到位，`patient_id` 作为内部关联键保留原值的理由能讲清；优秀 = 演示一次"AI 问数拒绝明细与隐私字段出网"的拦截过程，并说明白名单机制。

**C07 数仓分层建模与维度设计**
- 能力描述：能按 `ods_ / dwd_ / dws_ / ads_ / dim_` 前缀与 `_detail / _1d / _1m / _td` 命名规范建表，声明粒度与职责。
- 达标标准：合格 = 每层至少 1 张表落地且命名、字段、粒度声明正确（ODS 贴源 + 批次字段、DWD 脱敏与标准编码、DWS 按主题聚合、ADS 指标结果）；良好 = 维表初始化完整（`dim_department` 10 科室含开放床位 177、`dim_fee_type` 9 类、`dim_disease` 10 病种、`dim_drg_group` 10 组权重、`dim_date` 覆盖 2024-01-01~2026-12-31）；优秀 = 能在不改核心框架的前提下独立设计一个新主题的 DWS + ADS 表并说明维表复用方案。

**C08 SQL 加工与查询性能优化**
- 能力描述：能写出可维护、可复核的加工 SQL，并通过预聚合与索引把查询性能做到设计目标内。
- 达标标准：合格 = 指标计算 SQL 结果与基线一致，无跨口径混算；良好 = ADS 表按 `(stat_date, dept_code, metric_code)` 建联合索引，关键查询执行计划走索引；优秀 = 单指标查询 ≤300 ms（设计目标），并能给出优化前后的执行计划与耗时对比。

**C09 指标口径定义与版本变更管理**
- 能力描述：能按"公式 + 来源表 + 维度 + 粒度 + 版本"五要素定义指标，并走完口径变更流程。
- 达标标准：合格 = ≥10 项指标定义五要素齐全，且与《指标口径手册》无冲突；良好 = 指标定义落 `metric_def` 表，支持指标目录检索与 `version` 参数取数；优秀 = 完成一次口径变更演练（提出 → 评估对 ADS 表与历史数据的影响 → 评审 → 更新 `metric_def` 与手册 → 重跑回刷 → 通知使用方），并保留新旧版本并行的取数证明。

**C10 指标计算实现与基线核对**
- 能力描述：能把口径变成可执行的指标任务，并用基线值证明算对了。
- 达标标准：合格 = M01 门诊人次、M03 门诊次均费用、M11 床位使用率、M12 平均住院日、M19 药占比、M24 CMI 六项必核指标与基线完全一致（9,000 / 425.15 元 / 88.89% / 9.54 天 / 30.00% / 1.09）；良好 = M01~M33 中 ≥28 项可计算并核对通过，不可计算项按 K8 约定返回 `null` 并标注"数据源待补充"；优秀 = 对 K1~K8 全部已知数据特征在图表或报表上落实口径角标与注释，并提交完整基线核对表（含差异原因列）。

**C11 Python 后端服务开发**
- 能力描述：能用 FastAPI + Pydantic v2 + SQLAlchemy 2.x 实现分层清晰、契约统一的服务端。
- 达标标准：合格 = 服务可启动，`/health` 与 ≥5 个业务接口可用；良好 = 严格分层（`api / services / models / schemas`），参数强校验，服务层只读 ADS/DWS 不直接查 ODS；优秀 = 实现 13 个模块路由（`/auth /system /datasource /task /file /quality /model /metric /dim /dashboard /analysis /report /ai`）中 ≥10 个，且 OpenAPI 文档可直接用于前端联调。

**C12 认证鉴权与数据权限**

- 达标标准：合格 = 三个默认账号（`admin` / `analyst01` / `dept_hn`）可登录，未登录访问返回 40101；良好 = `dept_hn` 仅能看到 HN 呼吸内科数据，跨科室访问返回 40302，院区维度（当前仅"本部"）隔离逻辑存在；优秀 = 横向越权测试用例全部通过，权限由依赖注入统一追加 `dept_code` 过滤条件，审计日志可追溯"谁、何时、查了什么、导出多少"。

**C13 API 契约设计与异常处理**
- 能力描述：能统一实现 `{"code","message","data","trace_id"}` 响应包与错误码体系，并保证全链路可追踪。
- 达标标准：合格 = 响应包结构正确，错误码实现 ≥5 个（0 / 40001 / 40101 / 40301 / 40302 / 40401 / 50001 / 50101 / 50301 中任选）；良好 = `trace_id` 从请求头贯通到日志与响应，参数校验失败返回 40001 而非 50001；优秀 = 用 OpenAPI 自动核对接口契约与实现零偏差，并演示大模型调用失败时返回 50301 的服务降级而非崩溃。

**C14 报表导出、订阅与操作审计**

**C15 前端组件开发与 ECharts 可视化**

**C17 大模型应用开发（NL2SQL / 报告生成 / 异常归因 / 知识问答）**
- 能力描述：能把自然语言问题解析为指标查询意图，走"模板优先 + 语义解析"路线生成受控 SQL，并加安全护栏。
- 达标标准：合格 = NL2SQL 跑通 ≥10 条问句，能返回数据、图表与文字结论；良好 = 意图识别正确映射到指标 + 维度 + 时间（如"上月呼吸科床位使用率趋势如何"→ M11 + `dept_code=HN` + 2025-06），guard 白名单校验生效，每次调用写 `ai_qa_log`（问题、SQL、行数、耗时、模型）；优秀 = 问数测试集 ≥50 条准确率 ≥85%（《项目说明》目标），DDL/DML/非白名单表/超行数四类拦截用例全部通过，且报告生成与异常归因（环比波动超 ±10% 触发，输出 Top3 归因）可稳定复现。

**C18 测试验证、容器化部署与工程协作**

### 4.2 各阶段能力训练要点

- **阶段一（T01~T02）**：训练"读文档 + 建骨架"的能力。核心不是写代码，而是建立基线意识：把 10 个科室、177 张开放床位、33 项指标编号、13 个接口模块先装进脑子，再动手。本阶段结束时必须能不看文档说出"我们做的是一条什么链路"。
- **阶段二（T03~T06）**：训练"把脏数据搬进来并且敢说它脏"的能力。ETL 不是 `read_csv` + `to_sql`，而是要交代批次、行数、幂等、质量与异常，这是数据工程与脚本小子的分水岭。
- **阶段三（T07~T09）**：训练"分层 + 口径"的双重能力，是全项目最难也最能拉开差距的阶段。DIM 缺一张维表，DWD 的 `drg_code` 就没来源；DWS/ADS 决定指标能否一次算对，`metric_def` 决定全平台口径是否唯一。
- **阶段四（T10~T12）**：训练"服务化交付"能力。重点从"能算出来"转为"能安全、可审计、按契约地被别人调用"：统一响应包、错误码、JWT、行级权限、P95。
- **阶段五（T13~T15）**：训练"数据表达"能力。核心判据是图表选型是否正确（趋势用折线、对比用柱状、构成用饼/环形、相关性用散点）以及页面是否有业务结论，而不是图表越多越好。
- **阶段六（T16~T18）**：训练"受控地使用大模型"的能力。强调模板优先、白名单护栏、全量留痕：大模型负责语义解析与文案，口径与 SQL 结构由平台控制。
- **阶段七（T19~T20）**：训练"工程收口"能力。测试用例覆盖单元、接口、前端冒烟、口径、性能、安全、AI 七类；缺陷要闭环；部署要能被第三人在新环境复现；答辩要能讲清取舍。

| 编号 | 指标 | 计算公式要点 | 基线期望值 | 容差 |

### 6.4 小组协作与个人贡献认定办法

1. **分工留痕**：小组须在阶段一提交"角色—任务—成员"对应表（对应 1.2 节五种角色），并在任务板（如周看板）上把 T01~T20 拆到人。
2. **贡献系数**：个人最终成绩 = 小组成绩 × 贡献系数，系数区间 **0.8~1.2**，小组内各成员系数平均值须为 1.0（不足 3 人时由指导教师核定）。个人最终成绩封顶 100 分。
3. **认定证据（至少三类）**：① Git 提交记录（提交次数、改动文件与代码行分布，须与自己声称负责的模块吻合）；② 阶段评审汇报与代码评审记录（谁提了意见、谁改的）；③ 答辩个人问答环节对本域问题的作答质量。
4. **系数评定规则**：主责 ≥2 个阶段核心任务且交付一次通过 → 1.1~1.2；完成分担任务、质量达标 → 1.0；参与度低或交付多次返工 → 0.8~0.9；未实际参与（证据缺失）→ 0.8 以下并按个人不合格处理。
5. **争议处理**：小组成员对系数的异议，先内部协商并留书面记录；无法达成一致的，由指导教师依据三类证据在 3 个工作日内裁定，裁定结果需双方签字确认。
6. **不可替代原则**：答辩时每名成员必须能独立讲清本人负责模块的"做了什么、为什么这样做、数据从哪来、出错怎么排查"，否则该成员成绩不得高于"合格"。

### 9.2 常见薄弱环节与提升建议

| 序号 | 薄弱环节（典型现象） | 风险 | 提升建议 | 达标判定 |
| --- | --- | --- | --- | --- |
| 1 | **只跑通流程，不懂口径**：指标算出来了，但说不清分子分母怎么来 | 一旦数据或口径变化立即失能；答辩必被问倒 | 逐项手写 M01/M03/M11/M12/M19/M24 的公式、来源表、粒度，并解释与相邻指标的关系 | 能不看文档口述六项必核指标公式与基线值 |
| 2 | **把 ODS 当分析层**：直接在贴源表上算指标、做看板 | 无标准化与脱敏，口径分散无法维护 | 强制"ODS 只落原文、DWD 做清洗脱敏、DWS 只聚合、ADS 才落指标"的四段纪律，并画一张各层字段流转图 | 任取一个指标能指出它经过的每一层表 |
| 3 | **ETL 不幂等**：重跑一次收入翻倍或人次翻倍 | 回刷即事故，数据不可信 | 用 `etl_batch_id` 做"按批次先删后插"，并固定统计窗口 2025-04-01~2025-06-30 | 同一批次执行两次，ADS 结果不变 |
| 4 | **查询期做重聚合**：接口里多表 join + 大聚合 | P95 超标，报表卡顿 | 指标在 ADS 预聚合落库，查询期只做过滤排序；按 `(stat_date, dept_code, metric_code)` 建联合索引 | 单指标查询 ≤300 ms、驾驶舱 P95 ≤3 s |
| 5 | **权限只在菜单层做**：隐藏按钮但接口仍可取全院数据 | 明显的数据越权与合规风险 | 把 `dept_code` 过滤放进依赖注入统一追加，并写越权测试用例（`dept_hn` 访问他科返回 40302） | 越权用例全部通过且审计可追溯 |
| 6 | **图表堆砌，没有结论**：一屏 8 个图，说不出所以然 | 视为"会画图但不会分析"，交付价值低 | 每个图表强制配一句业务结论与口径角标；科室对比类必须附"业务量均匀、不用于绩效排序"的说明 | 每张看板能 60 秒讲完"看什么、异常在哪、建议是什么" |
| 7 | **NL2SQL 自由拼 SQL**：绕过指标定义直接让大模型写查询 | 口径漂移、注入风险、无法审计 | 坚持"模板优先 + 语义解析"，所有 SQL 经白名单 `guard.py`，每次调用落 `ai_qa_log` | 四类护栏用例（DDL/DML/非白名单表/超行数）全部拦截成功 |
| 8 | **文档与代码脱节**：代码改了文档没改，成果物不成套 | 验收时口径与实现对不上，无法交接 | 每阶段评审前 1 日同步文档；用交叉引用链接互相校验；变更走口径变更流程并留版本 | 第三方仅凭文档即可复现部署与指标计算 |

### 附录 A 术语表

| 术语 | 含义 |
| --- | --- |
| ODS（贴源层） | 与源系统字段一致的原始数据层，保留批次字段 `etl_batch_id` / `etl_load_time`，不做业务加工 |
| DWD（明细层） | 去重、空值处理、编码标准化、隐私脱敏后的明细宽表，一行一业务事件 |
| DWS（汇总层） | 按主题 + 时间粒度（日/月）聚合的汇总表，如 `dws_bed_1d` |
| ADS（应用层） | 指标结果表，直接支撑看板与接口，全平台口径唯一实现处 |
| DIM（维表层） | 科室、费别、号别、病种、DRG 分组、日期等公共维表与字典 |
| 登记口径 | 就诊登记时的汇总费用字段（`his_outpatient.fee_amount`、`his_inpatient.total_fee`），用于 M03、M13 |
| 流水口径 | 逐笔收费流水（`his_charge.amount`），用于 M07、M15、M16 及费别结构类指标 |
| 财务口径 | 财务日报导出数据（`finance_excel.revenue` 等），用于 M17/M18/M19/M20 默认取值与对账 |
| DRG / DIP | 疾病诊断相关分组 / 病种分值付费，医疗费用与绩效管理的基础分组方法 |
| CMI | 病例组合指数，出院病例 DRG 权重均值，反映收治病例的技术难度（本项目基线 1.09） |
| 费用消耗指数 / 时间消耗指数 | 实际费用（住院日）与同组标准值之比，>1 表示资源消耗超支（本项目基线均约 0.9174） |
| 实际占用总床日数 | 出院患者住院天数之和（M10，基线 14,317 床日），床位使用率与平均住院日的分子 |
| 床位使用率 | 实际占用总床日数 ÷（开放床位数 × 统计天数）（M11，基线 88.89%） |
| 平均住院日 | 实际占用总床日数 ÷ 出院人次（M12，基线 9.54 天） |
| 床日 | 一位患者占用一张病床一天，当日出入院记 0 床日（本数据集 17 例） |
| 次均费用 | 统计期费用合计 ÷ 对应人次（M03 门诊、M13 住院） |
| 药占比 / 耗占比 | 药品收入 / 耗材收入 占医疗收入的比例（M19 基线 30.00%、M20 基线 10.00%，财务口径） |
| 窗口首尾效应 | 建仓统计窗口截断导致的分布异常，如 2025-06-30 集中出院 190 例 |
| 基线值 | 《指标口径手册》第 5 章给出的指标期望值，是测试断言与验收比对的唯一基准 |
| NL2SQL | 自然语言转 SQL，支撑智能问数；本项目采用"模板优先 + 语义解析"路线 |
| Prompt / 护栏（guard） | 大模型提示词模板 / SQL 白名单安全校验（只读、强制 limit、禁 DDL/DML） |
| RBAC | 基于角色的访问控制；本项目角色为 ADMIN 管理员、ANALYST 运营分析师、DEPT_USER 科室用户 |
| 数据权限（行级） | 按 `dept_code` 与院区（当前仅"本部"）限制可见数据范围，由依赖注入统一追加过滤条件 |
| JWT / Bearer | 无状态令牌鉴权方式，接口通过 `Authorization: Bearer <token>` 传递 |
| 统一响应包 | `{"code":0,"message":"success","data":{...},"trace_id":"..."}`，错误码 0/4xx/5xxx |
| trace_id | 单次请求的追踪标识，贯穿中间件、服务、日志与响应，便于排障 |
| 幂等 | 同一批次重复执行不改变结果，本项目以 `etl_batch_id` 先删后插保证 |
| 脱敏 | 姓名掩码（`张**`）、身份证保留前 6 后 4、手机号保留前 3 后 4 |
| T+1 | 数据在业务发生次日完成加工入库的批处理节奏 |
| P95 | 95 分位响应时间，本项目常规报表目标 ≤3 s |
