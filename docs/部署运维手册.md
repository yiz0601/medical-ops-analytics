## 1. 文档说明与读者对象

### 1.1 本手册解决什么问题

本手册给出《医疗运营数据主题分析平台》从零部署到日常运维的完整操作路径，覆盖：

- 部署架构、软硬件与端口要求；
- 目录与持久化规划、日志位置；
- 部署前准备（Docker 安装、镜像源、`.env` 变量、目录权限、防火墙）；
- 数据库初始化与数据核对（含基线校验 SQL）；
- 三容器编排的分步实施与验收清单（含预期输出与验证清单）；
- 启停、升级、回滚；
- 日常巡检、日志管理、备份恢复、监控指标、定时任务；
- 13 类故障场景的排查与处置；
- 安全加固、容灾演练与附录速查。

## 2. 部署架构与环境要求

### 2.1 部署架构（三容器）

与《[概要设计](概要设计.md)》第 2.3 节部署架构一致，仅在图上标注了真实容器名、网络与卷：

```
                        ┌─────────────────── 宿主机（Linux / Windows + Docker Engine）───────────────────┐
                        │                                                                              │
   Browser ──HTTP:80──▶ │  ┌──────────────────────────┐                                                │
                        │  │ moa-frontend             │                                                │
                        │  │ nginx:1.27-alpine        │                                                │
                        │  │ · 静态资源 /usr/share/nginx/html                                               │
                        │  │ · 站点配置挂载 deploy/nginx.conf（只读）                                        │
                        │  └───────────┬──────────────┘                                                │
                        │              │ /api/ 、/docs 、/redoc 、/health 反向代理                          │
                        │              ▼                                                               │
                        │  ┌──────────────────────────┐      ┌──────────────────────────────┐          │
                        │  │ moa-backend              │─3306▶│ moa-mysql                    │          │
                        │  │ python:3.11-slim         │      │ mysql:8.0                    │          │
                        │  │ uvicorn app.main:app     │      │ utf8mb4 / +08:00 / max_conn=500        │
                        │  │ 容器内 :8000（expose）    │      │ 卷 mysql_data → /var/lib/mysql         │
                        │  │ 卷 upload_data → /app/uploads    │ 只读挂载 ../sql → initdb.d/sql        │
                        │  │ 只读挂载 ../data → /app/data     └──────────────────────────────┘          │
                        │  └───────────┬──────────────┘                                                │
                        │              │ HTTPS 出站（可选，NL2SQL / 报告生成）                             │
                        └──────────────┼───────────────────────────────────────────────────────────────┘
                                       ▼
                            LLM API（OpenAI 兼容协议，Nginx 侧超时 180s）
```

**网络与暴露关系（与 `deploy/docker-compose.yml` 完全一致）**

| 项 | 值 | 出处 |
| --- | --- | --- |
| 编排网络 | `medical-net`（driver: bridge） | compose `networks` |
| 仅对外暴露的端口 | `80`（`frontend` 服务 `ports: "80:80"`） | compose `frontend.ports` |
| MySQL 端口映射 | `3306:3306`（默认对宿主机开放，安全加固见 10.3） | compose `mysql.ports` |
| 后端端口 | `8000` 仅 `expose`，**不发布到宿主机** | compose `backend.expose` |
| 服务间寻址 | Nginx 用 `server backend:8000`；后端用 `DB_HOST: mysql` | nginx.conf / compose |

> 说明：后端以服务名 `mysql` 直连数据库（容器网络内 DNS），因此**服务名不可随意改名**；如改名必须同步修改 compose 中的 `DB_HOST` 与 `nginx.conf` 中的 `upstream` 地址。

### 2.2 硬件要求

以下为**规划估算**（非实测），面向 10 万行级模拟数据集的演示/生产小规模场景：

| 规格项 | 最低要求 | 推荐配置 | 说明 |
| --- | --- | --- | --- |
| CPU | 2 vCPU | 4 vCPU | 前端构建阶段（`npm run build`）与后端镜像构建阶段较吃 CPU，首次构建建议临时给足 4 核 |
| 内存 | 4 GB | 8 GB | 三容器常驻估算：MySQL 约 1.0–1.5 GB、后端（2 worker + pandas）约 0.5–1.0 GB、Nginx 数十 MB；另需为构建过程预留 1–2 GB |
| 磁盘 | 40 GB | 100 GB SSD | 构成见下方说明；SSD 对 MySQL 建库与 ADS 查询响应影响明显 |
| 带宽 | 5 Mbps | 20 Mbps | 前端压缩后静态资源小，主要流量为 JSON 接口与导出文件；大模型出站为可选且为低频调用 |
| swap | 2 GB（或禁用） | 2 GB | 建议开启 2 GB 防 OOM 硬杀，但不可依赖 swap 承载 MySQL |

**磁盘空间构成（估算，标注为规划值）**

| 组成 | 估算占用 | 说明 |
| --- | --- | --- |
| MySQL 镜像（`mysql:8.0`） | 约 600 MB | 官方镜像解压后体量，具体以 `docker image ls` 实际值准 |
| 后端镜像（`python:3.11-slim` + 依赖） | 约 0.8–1.5 GB | 依赖含 pandas、reportlab、cryptography、openpyxl 等二进制轮子，属体积主要来源 |
| 前端镜像（`nginx:1.27-alpine` + `dist`） | 约 50–120 MB | 构建阶段 `node:20-alpine` 层仅在构建期占空间 |
| 构建缓存（BuildKit） | 约 1–2 GB | 可用 `docker builder prune` 回收 |
| `mysql_data` 卷 | 200 MB–1 GB | 含 InnoDB 表空间、binlog、undo；导入 5 万行级数据后仍属小体量 |
| `data/` 模拟数据集 | 约 4.1 MB | 6 个 CSV 合计 4,266,695 字节，容器内为只读挂载 |
| `upload_data` 卷 | 视上传量 | 财务日报等文件，单文件受 Nginx `client_max_body_size 50m` 限制 |
| 备份目录 | ≥ 3 × 数据卷大小 | 见 8.3 保留策略 |

| 软件 | 版本要求 | 说明 |

### 2.4 端口规划表

| 端口 | 宿主监听 | 归属容器/进程 | 用途 | 是否对外 | 备注 |
| --- | --- | --- | --- | --- | --- |
| **80** | `0.0.0.0:80` | `moa-frontend`（Nginx） | 前端静态资源 + `/api/`、`/docs`、`/redoc`、`/health` 反向代理 | **是**（唯一业务对外端口） | 生产建议前置 HTTPS，见 10.4 |
| **3306** | `0.0.0.0:3306` | `moa-mysql` | MySQL 8.0 数据库 | 默认对外 | **安全建议**：公网环境应在安全组/防火墙关闭 3306；如仅需宿主调试，建议后续将映射改为 `127.0.0.1:3306:3306`（属 compose 变更，本手册不修改） |
| **8000** | 不监听宿主 | `moa-backend` | FastAPI/Uvicorn 服务，仅 `expose` | **否**（仅 `medical-net` 内可达） | 容器内 `EXPOSE 8000`，由 Nginx 反代 |
| **5173** | 不监听宿主 | 前端 Vite dev server（本地开发） | 开发期热更新调试 | 否 | 仅 `npm run dev` 本地开发占用，容器部署不涉及；`vite.config.js` 已配 `/api` 代理到 `127.0.0.1:8000` |
| 4173 | 不监听宿主 | `npm run preview` | 构建产物预览 | 否 | 非部署链路，可选 |
| 443 | — | Nginx（可选） | HTTPS | 生产建议 | **待补充**：当前 `nginx.conf` 仅监听 80，启用 HTTPS 需新增 server 块与证书挂载（见 10.4） |

**端口冲突自查命令**

```bash
# Linux
ss -lntp | grep -E ':(80|3306|8000|5173)\b'
```

```powershell
# Windows PowerShell
Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -in 80,3306,8000,5173 } |
  Select-Object LocalAddress,LocalPort,OwningProcess
```

> Windows 常见冲突：IIS / World Wide Web Publishing Service 占用 80；本机已装 MySQL 占用 3306（`Get-Service W3SVC,MySQL80`）。

### 3.2 容器内路径映射（真实挂载）

| 宿主机路径（相对项目根） | 容器内路径 | 容器 | 模式 | 用途 |
| --- | --- | --- | --- | --- |
| 命名卷 `mysql_data` | `/var/lib/mysql` | `moa-mysql` | 读写 | 数据库数据持久化（**最关键**） |
| 命名卷 `upload_data` | `/app/uploads` | `moa-backend` | 读写 | 文件接入上传文件 |
| `../data`（即 `data/`） | `/app/data` | `moa-backend` | **只读** | 模拟数据集（ETL 读取源） |
| `../sql`（即 `sql/`） | `/docker-entrypoint-initdb.d/sql` | `moa-mysql` | **只读** | 数仓脚本存放（见下方重要说明） |
| `deploy/nginx.conf` | `/etc/nginx/conf.d/default.conf` | `moa-frontend` | **只读** | 站点配置（修改宿主文件后需 reload/重启容器，无需重构镜像） |

> **重要说明（MySQL 初始化行为）**：官方 `mysql:8.0` 镜像只会自动执行 `/docker-entrypoint-initdb.d/` **顶层**的 `*.sql` / `*.sh` / `*.sql.gz` 文件，**不会递归子目录**。
> 本项目把 `sql/` 整个目录挂载成了 `initdb.d/sql`（一个子目录），因此 `sql/dim/*.sql` 等脚本**不会被自动执行**，必须按 5.2 节手工执行。
> 同时，初始化仅在 `mysql_data` 卷为空（首次启动）时触发，已有数据后再加脚本也不会执行。

### 3.3 需要持久化的路径

| 对象 | 类型 | 实际名称 / 位置 | 是否必须备份 |
| --- | --- | --- | --- |
| MySQL 数据 | Docker 命名卷（逻辑名 `mysql_data`） | 实际卷名形如 `deploy_mysql_data` | **必须**（RPO 目标见 8.3） |
| 上传文件 | Docker 命名卷（逻辑名 `upload_data`） | 实际卷名形如 `deploy_upload_data` | **必须** |
| 站点配置 | 宿主机文件 `deploy/nginx.conf` | 纳入 Git 版本控制 | 建议（随代码） |

| 模拟数据集 | 宿主机目录 `data/` | 纳入 Git/制品库 | 建议 |
| 后端应用日志 | 容器内 `/app/logs` | **未挂载，容器重建即丢失** | 待补充（见 8.2 建议方案） |

#### 4.3.3 编写 `.env` 的注意事项

1. **不要使用 `$`**：compose 会把它当变量插值，若口令必须含 `$`，请写为 `$$`。
2. **不要加引号**：`.env` 中的 `MYSQL_PASSWORD="xxx"` 会把引号作为值的一部分传给 MySQL，导致后端连不上。
3. **不要留空格**：`KEY = value` 形式在部分 compose 版本下解析异常，请写 `KEY=value`。
4. **编码**：必须 UTF-8 无 BOM（Windows 记事本另存为「UTF-8」时注意 BOM 选项）。
5. **一致性**：`MYSQL_*` 与 `DB_NAME/DB_USER/DB_PASSWORD` 在 compose 中已同源绑定，**只改 `MYSQL_*` 即可**，不要单独改 `DB_*`。
6. **改口令后**：`mysql_data` 卷已初始化时，改 `.env` 的 `MYSQL_PASSWORD` **不会**修改库内账号口令，需按 8.3.3 在库内同步修改（详见 9.3）。

### 4.5 防火墙与安全组

**原则**：对外仅开放 `80`（启用 HTTPS 后追加 `443`），运维端口 `22` 限来源 IP；`3306` **不对公网开放**；`8000`/`5173` 永不对公网开放。

#### Linux — ufw（Ubuntu/Debian）

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from <运维机网段，如 10.0.0.0/8> to any port 22 proto tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw deny 3306/tcp
sudo ufw enable
sudo ufw status numbered
```

#### Linux — firewalld（Rocky/Alma/CentOS Stream）

```bash
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="<运维机IP>/32" port port="3306" protocol="tcp" accept'
sudo firewall-cmd --permanent --remove-port=3306/tcp 2>/dev/null || true
sudo firewall-cmd --reload
sudo firewall-cmd --list-all
```

#### Windows — 高级防火墙

```powershell
New-NetFirewallRule -DisplayName "MOA HTTP 80"  -Direction Inbound -Protocol TCP -LocalPort 80  -Action Allow
New-NetFirewallRule -DisplayName "MOA HTTPS 443" -Direction Inbound -Protocol TCP -LocalPort 443 -Action Allow
# 3306 仅允许运维机访问（示例网段，请替换）
New-NetFirewallRule -DisplayName "MOA MySQL 3306 (ops only)" -Direction Inbound -Protocol TCP -LocalPort 3306 `
  -RemoteAddress 10.0.0.0/8 -Action Allow
New-NetFirewallRule -DisplayName "MOA MySQL 3306 block" -Direction Inbound -Protocol TCP -LocalPort 3306 -Action Block
```

#### 云主机安全组（控制台操作要点）

| 方向 | 协议/端口 | 源 | 说明 |
| --- | --- | --- | --- |
| 入站 | TCP 80 | `0.0.0.0/0` | 前端入口 |
| 入站 | TCP 443 | `0.0.0.0/0` | 启用 HTTPS 后 |
| 入站 | TCP 22 | 运维机固定 IP | 禁止全网 |
| 入站 | TCP 3306 | 仅跳板/DBA 固定 IP（或直接不开放） | **必须收敛** |
| 出站 | TCP 443 | LLM 服务域名/IP（可选） | 智能分析出站；不使用可全禁 |

> 校验端口未暴露：从外网执行 `nc -zvn <公网IP> 3306` / `Test-NetConnection <公网IP> -Port 3306` 应失败。

## 5. 数据库初始化

### 5.1 建库建账号与权限最小化

**当前自动化程度**：`mysql:8.0` 首次启动时，会依据 `MYSQL_DATABASE` / `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_ROOT_PASSWORD` 自动创建库 `medical_ops` 与账号 `moa`，并执行官方镜像的默认授权（`moa` 对 `medical_ops.*` 拥有全部权限）。
**该默认授权偏大（含 DDL）**，生产环境必须按下列步骤收权，或改用独立账号体系。

#### 5.1.1 字符集与时区基线（已由 compose 固化）

`docker-compose.yml` 中 mysql 的启动参数已固化以下基线，**无需再改**：

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `--character-set-server` | `utf8mb4` | 库表默认字符集，支持中文与 emoji |
| `--collation-server` | `utf8mb4_general_ci` | 排序规则（与 `sql/README.md` 中的建库语句一致） |
| `--default-time-zone` | `+08:00` | 会话/全局时区东八区，避免时间偏移 |
| `--max_connections` | `500` | 连接上限（后端 2 worker 场景有充足余量） |
| 环境 `TZ` | `Asia/Shanghai` | 容器系统时区 |

#### 5.1.2 账号与权限设计（目标态）

| 账号 | 用途 | 权限范围 | 是否允许 DDL |
| --- | --- | --- | --- |
| `root` | DBA 维护（建库建表、迁移、备份） | 全局 | 是 |
| `moa_etl` | ETL 任务：ODS 写入、DWD/DWS/ADS 加工 | `SELECT, INSERT, UPDATE, DELETE` on `medical_ops.*`（可按层细分） | **否** |
| `moa_app` | 后端应用连接（查询优先） | `SELECT` on `ads_%`、`dws_%`、`dim_%`；系统表（用户/角色/审计/任务）需 `SELECT, INSERT, UPDATE` | **否** |
| `moa`（compose 自动创建） | 当前默认连接账号 | 建议按 5.1.3 收权后作为 `moa_app` 使用，或弃用 | 收权后为否 |

> **权限边界要点**
> - 应用账号仅读 ADS/DWS/DIM，**禁止访问 ODS**（ODS 含隐私原始字段，按《概要设计》第 10 章仅 DBA/ETL 可读）。
> - 应用账号**禁止 DDL**（`CREATE/ALTER/DROP/INDEX/REFERENCES/CREATE VIEW/TRIGGER`），表结构变更一律走 DBA 迁移流程。
> - ETL 账号仅有 DML，避免误删表结构；`DELETE` 权限用于「按 `etl_batch_id` 幂等重跑」。

#### 5.1.3 执行脚本（在容器内以 root 执行）

```bash

docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql sh -lc '
mysql -uroot -p"$MYSQL_ROOT_PASSWORD" <<SQL

-- 3) 收权：先回收 compose 默认授予 moa 的全部权限（如继续使用 moa 作为应用账号）
REVOKE ALL PRIVILEGES, GRANT OPTION FROM "moa"@"%";

-- 4) 应用账号：只读 ADS/DWS/DIM（比例处可按详细设计的表清单细化为逐表授权）

GRANT SELECT ON medical_ops.`ads\_dashboard\_%` TO "moa_app"@"%";
GRANT SELECT ON medical_ops.`ads\_report\_%` TO "moa_app"@"%";

GRANT SELECT ON medical_ops.`dim\_%` TO "moa_app"@"%";

-- 5) ETL 账号：各层 DML（不含 DDL）
GRANT SELECT, INSERT, UPDATE, DELETE ON medical_ops.* TO "moa_etl"@"%";

-- 6) 若仍以 moa 作为后端连接账号，则给予与 moa_app 相同的只读权限
GRANT SELECT ON medical_ops.`ads\_kpi\_%` TO "moa"@"%";

GRANT SELECT ON medical_ops.`ads\_report\_%` TO "moa"@"%";
GRANT SELECT ON medical_ops.`dws\_%` TO "moa"@"%";
GRANT SELECT ON medical_ops.`dim\_%` TO "moa"@"%";

FLUSH PRIVILEGES;
SQL
'
```

### 5.2 SQL 脚本执行顺序

**当前状态：`sql/ods/`（`ods_tables.sql`、`verify_ods.sql`）与 `sql/dwd/`（`dwd_tables.sql`）已于阶段二交付；`sql/dim/`、`sql/dws/`、`sql/ads/` 仍为空目录（待阶段三）。** 因此本章给出完整的执行顺序与命令：已交付脚本可直接执行，未交付脚本会被跳过或执行报错（属预期）。

`dim → ods → dwd（含 ETL 入库）→ dws → ads`（与 `sql/README.md` 一致）：

| 顺序 | 目录 | 计划脚本（按 sql/README.md） | 说明 | 交付阶段 |
| --- | --- | --- | --- | --- |
| 1 | `sql/dim/` | `01_dim_department.sql`、`02_dim_fee_type.sql`、`03_dim_disease_drg.sql`、`04_dim_date.sql` | 科室 10 行、费别 9 行、病种/DRG 各 10 行、号别字典、日期维 | 阶段三 |
| 2 | `sql/ods/` | `01_create_ods_tables.sql`、`02_ods_load_procedures.sql` | 贴源建表（字段与 CSV 一致 + `etl_batch_id`、`etl_load_time`） | 阶段三 |
| 3 | `backend/etl/jobs/` | `run_all.py`（采集总入口） | 将 `data/` 六个 CSV 装入 ODS，写入批次号 | 阶段二 |
| 4 | `sql/dwd/` | `01_create_dwd_tables.sql`、`02_dwd_transform.sql` | 清洗、编码标准化、**隐私脱敏**（姓名 `张**`、证件号前 6 后 4、手机号前 3 后 4） | 阶段三 |
| 5 | `sql/dws/` | `01_create_dws_tables.sql`、`02_dws_aggregate.sql` | 主题 + 时间粒度聚合（日/月） | 阶段三 |
| 6 | `sql/ads/` | `01_create_ads_tables.sql`、`02_ads_kpi_calc.sql`、`03_ads_dashboard.sql` | 指标结果表与看板宽表，供后端直查 | 阶段三 |

#### 执行方式（Linux）

```bash
# 前提：已在项目根目录，deploy/.env 已创建，mysql 容器状态为 healthy
for f in sql/dim/*.sql sql/ods/*.sql sql/dwd/*.sql sql/dws/*.sql sql/ads/*.sql; do
  [ -e "$f" ] || { echo "跳过（不存在，待阶段三交付）：$f"; continue; }
  echo "==> 执行 $f"
  docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql sh -lc \
    'mysql --default-character-set=utf8mb4 -uroot -p"$MYSQL_ROOT_PASSWORD" medical_ops' < "$f" \
    || { echo "!!! 失败：$f"; break; }
done
```

#### 执行方式（Windows PowerShell）

```powershell
Set-Location D:\medical_data_analyze_platform

$files = @()
foreach ($d in 'dim','ods','dwd','dws','ads') {
  $files += Get-ChildItem -Path "sql\$d" -Filter *.sql -ErrorAction SilentlyContinue
}
if ($files.Count -eq 0) {
  Write-Host "sql/ 下暂无 .sql 脚本（待阶段三交付），本步骤跳过。"
}
foreach ($f in $files) {
  Write-Host "==> 执行 $($f.FullName)"
  # PowerShell 不支持 < 重定向，用管道传入；必须加 -T 关闭 TTY，否则会吞输入
  Get-Content -Raw -Encoding UTF8 $f.FullName |
    docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql sh -lc `
      'mysql --default-character-set=utf8mb4 -uroot -p"$MYSQL_ROOT_PASSWORD" medical_ops'
  if ($LASTEXITCODE -ne 0) { Write-Host "!!! 失败：$($f.Name)"; break }
}
```

> **必须注意**
> 1. Windows 下务必用 `-T`（禁用 TTY 分配），否则 `docker compose exec` 会吞掉标准输入导致脚本「执行成功但没建表」。
> 2. 中文 SQL 文件必须以 UTF-8 保存，并显式带 `--default-character-set=utf8mb4`，否则出现乱码（见 9.10）。
> 3. 重跑与回刷必须按 `etl_batch_id` 幂等删除后重插（`sql/README.md` 约定），不可直接重复 `INSERT` 造成数据翻倍。
> 4. **不要**依赖 `docker-entrypoint-initdb.d` 自动执行：该挂载点是 `initdb.d/sql` 子目录，官方镜像不递归（见 3.2 说明）。

> **构建失败常见点**
> - `npm run build` 报 `Could not resolve entry module "index.html"`：**阶段一的预期现象**（`frontend/src` 仅有 `.gitkeep`，无 `index.html` 入口），前端页面阶段五补齐后即可构建；现阶段请仅构建后端。

| 日志 | 推荐策略 | 当前实现 |

#### 8.3.2 数据库备份（推荐方式）

```bash

mkdir -p backup/mysql

  sh -lc 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --quick --routines --triggers \
          --events --default-character-set=utf8mb4 --databases medical_ops' \

ls -lh "backup/mysql/medical_ops_${TS}.sql.gz"
gzip -t "backup/mysql/medical_ops_${TS}.sql.gz" && echo "备份文件完整性 OK"
```

```powershell
# Windows PowerShell（用 gzip 压缩需 Git Bash 或 7-Zip；此处给出未压缩版本，最稳妥）
Set-Location D:\medical_data_analyze_platform
New-Item -ItemType Directory -Force backup\mysql | Out-Null

$out = "backup\mysql\medical_ops_$ts.sql"

# 关键：用 cmd /c 做重定向，PowerShell 的 > 会把输出转成 UTF-16 破坏 SQL 文件
cmd /c "docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql sh -lc ""mysqldump -uroot -p`$MYSQL_ROOT_PASSWORD --single-transaction --quick --routines --triggers --events --default-character-set=utf8mb4 --databases medical_ops"" > $out"

```

> **Windows 备份常见坑**：`mysqldump | Set-Content` 或 `>` 会写入 UTF-16/加 BOM，恢复时 MySQL 报语法错误。务必使用 `cmd /c "... > file"` 或 `[System.IO.File]::WriteAllBytes` 保存原始字节流。

### 8.4 监控指标建议

| 维度 | 指标 | 采集方式（无独立监控系统时） | 建议阈值/告警 |
| --- | --- | --- | --- |
| 可用性 | `/health` 探测成功率 | 外部定时 `curl`（1 分钟） | 连续 3 次失败告警 |
| 可用性 | 容器重启次数 | `docker inspect -f '{{.RestartCount}}' moa-backend` | > 2 次/小时告警 |
| 响应时间 | 接口 P95 | 由 Nginx 访问日志 `$request_time` 统计（当前日志格式为默认格式，未含耗时）→ 建议后续加 `log_format` 记录 `$request_time`（属 nginx.conf 变更，本手册不修改） | 常规报表 P95 ≤ 3 s（设计目标） |
| 错误率 | HTTP 5xx 比例 | 访问日志统计 ` 50[0-9] ` | > 0.5% 告警 |
| 错误率 | 应用异常数 | `docker compose logs backend` 中 `ERROR/Traceback` 计数 | 突增 3 倍告警 |
| 资源 | 容器 CPU/内存 | `docker stats --no-stream` | 单容器 CPU > 85%、内存 > 85% 或 `OOMKilled` 告警 |
| 数据库 | `Threads_connected` | `SHOW STATUS LIKE 'Threads_connected'` | > 300 预警，> 450 告警（上限 500） |
| 数据库 | `Innodb_row_lock_waits` / `Slow_queries` | `SHOW GLOBAL STATUS` | 环比突增告警 |
| 数据库 | 连接失败 `Aborted_connects` | `SHOW GLOBAL STATUS` | 持续增长排查网络/口令 |
| 磁盘 | 宿主磁盘使用率 | `df -h` | > 80% 预警，> 90% 告警 |
| 磁盘 | 卷大小 | `docker system df -v` | 单卷增速异常告警 |
| 容器健康 | `docker events` 中的 `health_status: unhealthy` | `docker events --filter event=health_status` | 出现即告警 |
| 备份 | 备份文件是否按计划生成 | 检查 `backup/` 时间戳 | 缺失当日备份即告警 |

| 任务 | 调度方式 | 当前状态 | 说明 |
| --- | --- | --- | --- |
| 采集/清洗/汇总/指标计算 | APScheduler（容器内进程，cron 表达式） | ⚠️ 待阶段二/三交付 | 依赖 `backend/etl/scheduler/`，当前为空骨架；调度器随后端进程启动 |
| 质量校验 | APScheduler 或随 ETL 串行执行 | ⚠️ 待阶段二交付 | 规则与报告表在阶段二/四落地 |
| 报表订阅推送 | APScheduler（`report_subscribe.cron`） | ⚠️ 待阶段四/六交付 | 见《概要设计》第 9 章 |
| 数据库备份 | 宿主 cron（下方示例） | ❌ 未配置 | 需运维手工落地 |
| 日志清理 | 宿主 cron | ❌ 未配置 | 需运维手工落地 |

**宿主 cron 示例（Linux）**

```bash

# 每周日 03:00 卷快照

# 每日 04:00 清理一周前的 Nginx 访问日志

```

## 9. 故障排查手册

> 通用前置：先执行 `docker compose -f deploy/docker-compose.yml --env-file deploy/.env ps` 与 `... logs --tail=200 <服务>`，90% 问题可在 3 分钟内定位。列出的排查命令在 Linux 与 Windows PowerShell 下写法一致，`grep` 在 Windows 可改用 `Select-String`。

### 9.1 容器起不来 / 反复重启

| 项 | 内容 |
| --- | --- |
| **现象** | `docker compose ps` 显示 `Restarting`，或 `Exited (1)`；`docker ps -a` 可见 `moa-mysql` 不断重启 |
| **可能原因** | ① `.env` 缺失或格式非法（含空格、引号、`$` 未转义）；② 端口 80/3306 被占用；③ 卷权限或磁盘满；④ MySQL 首次初始化失败（`mysql_data` 半初始化）；⑤ 内存不足被 OOM 杀 |
| **排查命令** | `docker compose -f deploy/docker-compose.yml --env-file deploy/.env ps -a`<br>`docker compose -f deploy/docker-compose.yml --env-file deploy/.env logs --tail=100 mysql`<br>`docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' moa-mysql`<br>`docker compose -f deploy/docker-compose.yml --env-file deploy/.env config \| head -n 30`<br>`df -h`；`ss -lntp \| grep -E ':(80\|3306)'` |
| **处理办法** | ① 修正 `.env`（见 4.3.3）后 `up -d`；② 释放端口或改映射（改映射需变更 compose，走评审）；③ 释放磁盘；④ 若 `mysql_data` 半初始化：**确认无需保留数据后** `docker compose ... down -v` 再 `up -d`（有数据则先按 8.3 备份尝试恢复）；⑤ 提升内存或减少后端 worker |
| **预防措施** | 部署前跑步骤 0 总检；`.env` 用模板生成；监控磁盘与 OOM；避免直接 `docker restart` 打断首次初始化 |

### 9.2 Nginx 502 Bad Gateway

| 项 | 内容 |
| --- | --- |
| **现象** | 浏览器访问 `/` 正常但 `/api/*`、`/health` 返回 `502 Bad Gateway`；`curl -sS http://127.0.0.1/health` 返回 502 |
| **可能原因** | ① 后端容器未启动/启动中；② 后端进程崩溃（未捕获异常导致 uvicorn 退出）；③ Nginx `upstream` 名称与 compose 服务名不一致；④ Nginx 在容器网络里解析不到 `backend`；⑤ 后端端口未监听（`uvicorn` 启动参数异常） |
| **排查命令** | `docker compose -f deploy/docker-compose.yml --env-file deploy/.env ps`<br>`docker exec moa-frontend sh -lc 'tail -n 50 /var/log/nginx/moa.error.log'`<br>`docker exec moa-backend sh -lc 'ps aux \| grep uvicorn'`<br>`docker exec moa-backend sh -lc 'python -c "import urllib.request;print(urllib.request.urlopen(\"http://127.0.0.1:8000/health\").read())"'`<br>`docker exec moa-frontend sh -lc 'getent hosts backend \|\| nslookup backend'`<br>`docker network inspect deploy_medical-net --format '{{range .Containers}}{{.Name}} {{end}}'` |
| **处理办法** | ① 后端未起：`up -d backend` 并看日志；② 崩溃：按日志修代码或回滚（7.4.1）；③ upstream 不匹配：恢复 `nginx.conf` 中 `server backend:8000;`（服务名不可随意改）；④ 网络重建后 DNS 异常：`docker compose ... down && up -d`（卷保留）；⑤ 端口异常：核对镜像 `CMD` 中 `--port 8000` 与 `expose: 8000` |
| **预防措施** | 保留 `moa-frontend` 的 `depends_on: backend`；后端加全局异常处理与健康探针；变更服务名走评审并同步改 `nginx.conf` |

### 9.3 数据库连接失败 / 时区偏移 / unhealthy 常驻

| 项 | 内容 |
| --- | --- |
| **现象** | 后端日志出现 `Can't connect to MySQL server on 'mysql:3306'`、`Access denied for user 'moa'@'...'`；或查询出的时间比预期晚 8 小时/早 8 小时；或 `moa-mysql` 长期 `unhealthy` |
| **可能原因** | ① 后端早于 MySQL 就绪启动；② `MYSQL_PASSWORD` 与库内账号口令不一致（**改了 `.env` 但卷已初始化**，MySQL 不会重置口令）；③ `DB_HOST/DB_PORT` 与实际服务名/端口不符；④ 账号权限被收权过头（连 `SELECT` 都没有）；⑤ 时区：容器 `TZ`、MySQL `--default-time-zone=+08:00`、客户端连接会话时区三者不一致；⑥ 连接数打满 |
| **排查命令** | `docker compose -f deploy/docker-compose.yml --env-file deploy/.env logs --tail=200 backend \| grep -i -E "mysql\|sqlalchemy\|access denied"`<br>`docker exec moa-mysql sh -lc 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SELECT user,host FROM mysql.user; SELECT @@global.time_zone, @@session.time_zone, NOW();"'`<br>`docker exec moa-mysql sh -lc 'mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" -h 127.0.0.1 -e "SELECT 1;"'`<br>`docker exec moa-backend date; docker exec moa-mysql date; date`<br>`docker exec moa-mysql sh -lc 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW STATUS LIKE \"Threads_connected\";"'` |
| **处理办法** | ① 等待 MySQL healthy 后再启后端（`depends_on` 已配，若被手工 `restart backend` 打断则重来）；② 口令不一致：在库内同步修改 `ALTER USER "$MYSQL_USER"@"%" IDENTIFIED BY '<.env 中的口令>';` 或改 `.env` 后重建后端；③ 修正 compose 中 `DB_HOST/DB_PORT`；④ 按 5.1.3 重新授权；⑤ 时区：确认三处一致（容器 `TZ=Asia/Shanghai`、MySQL `+08:00`、后端连接串如设置 `init_command=SET time_zone='+08:00'` 需与之一致），统一以东八区为准；⑥ 连接数：见 9.7 |
| **预防措施** | 不改已初始化环境的口令；变更口令走「库内改 + `.env` 改 + 重建后端」三步；巡检纳入时区核对（6.6 第 6 项）；应用连接串统一时区配置并在阶段四固化到 `app/core/config` |

### 9.4 健康检查不通过（unhealthy）

| 项 | 内容 |
| --- | --- |
| **现象** | `docker compose ps` 中 `moa-backend` 显示 `(unhealthy)`；`depends_on` 服务不启动；或 `moa-mysql` 一直 `(starting)` |
| **可能原因** | ① `/health` 路由被改或路径变更；② 后端启动耗时长（依赖加载慢），超过 `start_period 20s + interval 20s × retries 5`；③ MySQL 口令与 `MYSQL_ROOT_PASSWORD` 不一致导致 `mysqladmin ping` 失败；④ 容器内缺少探针命令（`python`/`curl`/`wget`）；⑤ 端口被改（`--port` 与探针 8000 不一致） |
| **排查命令** | `docker inspect -f '{{json .State.Health}}' moa-backend`（看 `FailingStreak` 与 `Output`）<br>`docker exec moa-backend sh -lc 'python -c "import urllib.request;urllib.request.urlopen(\"http://127.0.0.1:8000/health\").read()"'`<br>`docker compose -f deploy/docker-compose.yml --env-file deploy/.env logs --tail=100 backend`<br>`docker exec moa-mysql sh -lc 'mysqladmin ping -h 127.0.0.1 -uroot -p"$MYSQL_ROOT_PASSWORD"'` |
| **处理办法** | ① 恢复 `main.py` 的 `/health`（响应体为 `{"code":0,"message":"success","data":{"status":"up","version":"0.1.0"}}`）；② 后端启动慢则临时提高 `start_period`（属 compose 变更）；③ 口令对齐（9.3）；④ 探针命令缺失则改用镜像内已有命令（后端镜像已装 `curl`，也可用 `curl -fsS http://127.0.0.1:8000/health`）；⑤ 端口对齐 |
| **预防措施** | `/health` 作为不可变更契约（阶段四实现其他路由时保留）；探针只用镜像内已安装命令；健康检查参数纳入变更评审 |

### 9.5 前端白屏 / 接口 404

| 项 | 内容 |
| --- | --- |
| **现象** | 访问首页 HTTP 200 但页面全白；或页面能开但所有接口 404；或刷新子路由 404 |
| **可能原因** | ① 构建产物缺失（阶段一 `frontend/src` 仅有 `.gitkeep`，`npm run build` 无入口，`dist` 为空 → Nginx 返回默认页/空页）；② JS 资源 404（`/assets/` 路径与 `base` 配置不一致）；③ 接口调用路径错误（漏 `/api` 前缀，或写成 `/api/v1/...` 但后端路由尚未注册）；④ 阶段一骨架现状：除 `/health`、`/api/v1/ping` 外**所有业务接口均未实现，404 属预期**；⑤ SPA 子路由刷新 404（`try_files` 被改） |
| **排查命令** | `docker exec moa-frontend sh -lc 'ls -l /usr/share/nginx/html \| head -n 20'`<br>`docker exec moa-frontend sh -lc 'tail -n 50 /var/log/nginx/moa.error.log'`<br>`docker exec moa-frontend sh -lc 'tail -n 50 /var/log/nginx/moa.access.log \| grep -E " 404 " \| tail -n 20'`<br>`curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1/api/v1/ping`<br>`curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1/assets/` |
| **处理办法** | ① 确认是否为阶段一预期（`/api/v1/ping` 通即部署正常，业务 404 等阶段四/五）；② 资源 404：核对 `vite.config.js` 的 `build.outDir: 'dist'` 与 Nginx `root /usr/share/nginx/html`；③ 接口路径：前端统一以 `/api/v1` 前缀调用，Nginx `location /api/` 不做前缀裁剪；④ 子路由：确认 `location / { try_files $uri $uri/ /index.html; }` 未被改动；⑤ 强制刷新/清缓存（`/assets/` 30 天缓存） |
| **预防措施** | 前端接口基址统一常量；Nginx 配置纳入 Git 评审；阶段五交付后补充「部署后前端冒烟用例」到测试计划 |

### 9.6 采集任务失败

| 项 | 内容 |
| --- | --- |
| **现象** | （阶段二后）任务列表出现 `FAILED`；ODS 表行数与基线不符；批次表出现重复 `etl_batch_id` |
| **可能原因** | ① 源文件缺失或格式变化（`data/` 为只读挂载，路径 `/app/data`）；② CSV 编码非 UTF-8（乱码后解析失败）；③ 表结构与源字段不一致（阶段三脚本未执行）；④ 权限不足（ETL 账号无 DML）；⑤ 重跑未按 `etl_batch_id` 幂等删除，导致主键冲突；⑥ 磁盘满导致写入中断 |
| **排查命令** | `docker exec moa-backend sh -lc 'ls -l /app/data/mock_his /app/data/files'`<br>`docker exec moa-backend sh -lc 'wc -l /app/data/mock_his/*.csv'`<br>`docker compose -f deploy/docker-compose.yml --env-file deploy/.env logs --tail=300 backend \| grep -i -E "etl\|batch\|csv"`<br>`docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql sh -lc 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW GRANTS FOR \"moa_etl\"@\"%\";"'`<br>`docker compose ... exec -T mysql sh -lc 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SELECT etl_batch_id, COUNT(*) FROM medical_ops.ods_his_outpatient_visit GROUP BY etl_batch_id;"'` |
| **处理办法** | ① 补齐/纠正源文件（保持 UTF-8 无 BOM）；② 编码问题用 9.10 处置；③ 先按 5.2 执行建表脚本；④ 按 5.1.3 授权；⑤ 按 `etl_batch_id` 删除后重插（`DELETE FROM ... WHERE etl_batch_id = ?`）；⑥ 清理磁盘后重跑 |
| **预防措施** | 任务前置校验（文件存在、行数、编码）；批次幂等写入为强制规范；失败任务告警到值班群；质量校验（≥95% 规则覆盖）作为任务后置门槛 |

### 9.7 指标查询超时 / 连接数打满

| 项 | 内容 |
| --- | --- |
| **现象** | 看板加载超过 10 秒或 `504`；后端日志出现 `TimeoutError`、`QueuePool limit ... overflow`；`Threads_connected` 接近 500 |
| **可能原因** | ① 查询直接扫 ODS/DWD 大表做多表关联聚合（违反「ADS 直查」设计）；② 缺索引或时间范围无分区；③ 后端 worker 少但并发高（`--workers 2`）；④ 连接池未回收，泄漏；⑤ Nginx `proxy_read_timeout 60s` 先于查询超时 |
| **排查命令** | `docker compose ... exec -T mysql sh -lc 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW FULL PROCESSLIST;"'`<br>`docker compose ... exec -T mysql sh -lc 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW GLOBAL STATUS LIKE \"Threads_%\" ; SHOW GLOBAL STATUS LIKE \"Slow_queries\";"'`<br>`docker compose -f deploy/docker-compose.yml --env-file deploy/.env logs --tail=200 backend \| grep -i -E "timeout\|pool"`<br>`docker stats --no-stream moa-backend moa-mysql` |
| **处理办法** | ① 强制走 ADS 预聚合表（设计目标 P95 ≤ 3 s）；② 补索引/限定时间范围；③ 评估提高 `--workers`（属 Dockerfile 变更，需重建镜像与容量评估）；④ 检查连接池配置与 `close` 逻辑；⑤ 必要时调整 Nginx 超时（属 nginx.conf 变更） |
| **预防措施** | 指标口径与查询语句评审（阶段三/四）；慢查询日志常态化开启；容量按 50 并发用户目标验证（设计目标） |

### 9.8 大模型调用超时或 Key 无效

| 项 | 内容 |
| --- | --- |
| **现象** | 智能问数/报告生成长时间无响应、返回 `401`/`403`/超时；Nginx 记录 `504`（AI 接口 180 s 超时） |
| **可能原因** | ① `LLM_API_KEY` 为空或过期（compose 默认 `LLM_API_KEY:-` 即空字符串）；② `LLM_BASE_URL`/`LLM_MODEL` 与提供方不匹配；③ 容器无出网权限（安全组/防火墙/代理）；④ 提示词过长导致耗时超 180 s；⑤ 提供方限流 |
| **排查命令** | `docker exec moa-backend sh -lc 'env \| grep -E "^LLM_" \| sed "s/\(LLM_API_KEY=\).*/\1***/"'`<br>`docker exec moa-backend sh -lc 'python -c "import urllib.request;print(urllib.request.urlopen(\"http://127.0.0.1:8000/health\").status)"'`<br>`docker exec moa-frontend sh -lc 'tail -n 50 /var/log/nginx/moa.error.log \| grep -i -E "upstream timed out\|504"'`<br>`docker compose -f deploy/docker-compose.yml --env-file deploy/.env logs --tail=200 backend \| grep -i -E "llm\|openai\|401\|timeout"`<br>容器内出网测试：`docker exec moa-backend sh -lc 'curl -sS -m 5 -o /dev/null -w "%{http_code}\n" https://api.openai.com/v1/models'` |
| **处理办法** | ① 补齐/轮换 `LLM_API_KEY` 后 `up -d backend`；② 校正 `LLM_BASE_URL`（须含 `/v1` 之类路径）与 `LLM_MODEL`；③ 放开出网或配置代理（需在容器环境变量中配置 `HTTPS_PROXY`，属 compose 变更）；④ 缩短输入/分批生成；⑤ 退避重试并联系提供方 |
| **预防措施** | Key 走 `.env` 与离线密码库（10.2）；上线前做一次 AI 链路连通性验证；`nginx.conf` 已针对 `^/api/v1/ai/` 单独放宽到 180 s，避免普通接口被拖长；Key 有效期纳入月检 |

### 9.9 磁盘满

| 项 | 内容 |
| --- | --- |
| **现象** | 写入失败；MySQL 报 `No space left on device`；容器重启；`docker ps` 显示容器异常 |
| **可能原因** | ① 容器标准输出日志（json-file）未限制体积；② 备份文件堆积未清理；③ `mysql_data` 中 binlog/慢查询日志增长；④ 构建缓存与悬空镜像堆积；⑤ Nginx 访问日志未轮转 |
| **排查命令** | `df -h`；`df -hi /var/lib/docker`<br>`docker system df -v`<br>`docker exec moa-mysql sh -lc 'du -sh /var/lib/mysql/* \| sort -h \| tail'`<br>`docker exec moa-frontend sh -lc 'ls -lh /var/log/nginx/'`<br>`du -sh backup/*`<br>`docker exec moa-mysql sh -lc 'ls -lh /var/lib/mysql \| grep -i bin'` |
| **处理办法** | 按 8.2.3 释放：`docker builder prune`、`docker image prune`、truncate Nginx 日志、清理过期备份、必要时 `PURGE BINARY LOGS BEFORE ...`（先在库内确认） |

### 9.10 中文乱码

| 项 | 内容 |
| --- | --- |
| **现象** | 页面显示 `??`/`????`/`æµ‹è¯•`；数据库查询中文为问号；导出的 SQL 恢复后中文丢失 |
| **可能原因** | ① 客户端连接未指定 `utf8mb4`；② 导入时用了 Windows 默认 GBK 或 UTF-16（PowerShell `>`/`Set-Content` 默认行为）；③ `.env`/SQL 文件带 BOM；④ 表/列字符集非 `utf8mb4`；⑤ 终端显示编码与数据无关（假乱码） |

### 9.11 内存溢出 / 容器 OOMKilled 重启

| 项 | 内容 |
| --- | --- |
| **现象** | `docker inspect -f '{{.State.OOMKilled}}' moa-backend` 为 `true`；容器无规律重启；页面偶发 502 |
| **可能原因** | ① 宿主内存不足（三容器 + 构建同时进行）；② 后端 pandas 一次性全量读大 CSV（`his_charge.csv` 44,078 行）；③ `--workers 2` × 连接池放大内存；④ MySQL `innodb_buffer_pool_size` 默认与宿主不匹配；⑤ 未配 swap 导致直接硬杀 |

| **处理办法** | ① 扩容内存或停止并行构建；② ETL 改为分块读取（`chunksize`）或 SQL 侧聚合；③ 评估降低 worker 数（Dockerfile CMD 变更需重建）；④ 通过 MySQL 配置调整 buffer pool（compose `command` 变更）；⑤ 配置 2 GB swap 兜底 |
| **预防措施** | 容量按 8 GB 推荐配置部署；构建与运行错峰；`docker stats` 与 OOM 事件纳入告警；ETL 内存使用写进阶段二验收要求 |

### 9.12 端口冲突（80 / 3306 被占用）

| 项 | 内容 |
| --- | --- |
| **现象** | `up -d` 报 `Bind for 0.0.0.0:80 failed: port is already allocated`；或 MySQL 无法映射 3306 |
| **可能原因** | 宿主已有 Nginx/Apache/IIS 占用 80；已安装本机 MySQL 占用 3306；上一个编排未清理干净 |

| **处理办法** | ① 停用占用方（`Stop-Service W3SVC`；`sudo systemctl stop nginx`）；② 或将前端改为其他宿主端口（compose `ports` 变更，需评审）；③ 清理残留：`docker ps -a \| grep 80` 后 `docker rm -f`；④ 已有本机 MySQL 时，评估是否让 `moa-mysql` 改映射端口 |

### 9.13 建表脚本未生效 / 表不存在

| 项 | 内容 |
| --- | --- |
| **现象** | 执行校验 SQL 报 `Table 'medical_ops.dim_department' doesn't exist`；重启 MySQL 后仍无表 |
| **可能原因** | ① **正常态**：`sql/` 各分层当前仅有 `.gitkeep`（阶段三才交付脚本）；② 误以为 `docker-entrypoint-initdb.d` 会自动执行——挂载点是 `initdb.d/sql` **子目录**，官方镜像不递归执行；③ 卷已初始化，初始化逻辑不会再触发；④ 手工执行时未加 `-T`，脚本被吞 |

**步骤 3：nginx.conf 增加 HTTPS server 与 301 跳转（示例片段）**

```nginx
# 80 端口全部 301 跳转到 HTTPS（/health 可保留明文直通，便于探活）
server {
    listen 80;
    server_name moa.example.com;
    location = /health { proxy_pass http://moa_backend/health; access_log off; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    http2 on;
    server_name moa.example.com;

    ssl_certificate     /etc/nginx/certs/server.crt;
    ssl_certificate_key /etc/nginx/certs/server.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 10m;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options    "nosniff" always;
    add_header X-Frame-Options           "SAMEORIGIN" always;
    add_header Referrer-Policy           "strict-origin-when-cross-origin" always;
    add_header Content-Security-Policy   "default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'" always;

    root  /usr/share/nginx/html;
    index index.html;
    charset utf-8;
    client_max_body_size 50m;

    location /            { try_files $uri $uri/ /index.html; }
    location /assets/     { expires 30d; add_header Cache-Control "public, max-age=2592000, immutable"; }
    location /api/        { proxy_pass http://moa_backend; proxy_set_header Host $host;
                            proxy_set_header X-Real-IP $remote_addr;
                            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
                            proxy_set_header X-Forwarded-Proto $scheme;
                            proxy_read_timeout 60s; }
    location ~ ^/api/v1/ai/ { proxy_pass http://moa_backend; proxy_read_timeout 180s; proxy_buffering off; }
}
```

### 11.1 故障场景与处置矩阵

| 场景 | 影响面 | 触发条件 | 首要处置 | 恢复目标 | 依赖前提 |
| --- | --- | --- | --- | --- | --- |
| **MySQL 宕机** | 全站只读/不可用（前端静态页仍可打开） | 容器退出、宿主重启、数据损坏 | ① `up -d mysql`；② 无法启动则 `logs` 定位；③ 数据损坏则 8.3.4 卷恢复 | 单容器重启：分钟级；卷恢复：≤ 2 小时（目标） | 每日逻辑备份 + 每周卷快照 |
| **磁盘故障** | 全站不可用 | 云盘故障/宿主磁盘损坏 | ① 更换云盘/挂载新磁盘；② 重新部署编排；③ 恢复 `mysql_data`、`upload_data` 卷与 `.env` | ≤ 4 小时（目标，含环境重建） | 备份在异机/对象存储；`.env` 有离线保管 |
| **误删数据**（表/库/卷被删） | 部分或全部数据缺失 | 误执行 `DROP`/`TRUNCATE`/`down -v` | ① 立即停写（`stop backend`）；② 按 8.3.3/8.3.4 从最近备份恢复；③ 5.4 校验基线 | 单表：≤ 1 小时；整库：≤ 2 小时（目标） | 备份文件可用且校验过 |
| **全站不可用** | 所有用户无法访问 | 宿主宕机、网络中断、误操作 `down -v`、端口被改 | ① 判断是宿主/网络/编排层；② 宿主正常则 `up -d --build`；③ 宿主异常则迁机重建 | ≤ 4 小时（目标） | 部署脚本、配置、备份齐备 |
| **后端进程崩溃** | 接口不可用，静态页可打开 | 代码缺陷、OOM | `restart: unless-stopped` 自动拉起；反复崩溃则回滚（7.4.1） | ≤ 10 分钟 | 保留上一版本镜像 tag |
| **大模型服务不可用** | 仅智能分析降级 | Key 失效、出网中断、提供方故障 | 关闭/降级 AI 功能，其余功能不受影响（`LLM_API_KEY` 为空即视为不可用） | 无硬性要求 | 功能解耦（AI 独立模块） |
| **磁盘满** | 写入失败、容器重启 | 日志/备份/数据集增长 | 按 8.2.3 清理 | ≤ 30 分钟 | 清理脚本与权限就绪 |

### 11.3 四个核心演练步骤

#### 演练一：MySQL 宕机与恢复

```bash
# 1) 制造故障：停止数据库
docker compose -f deploy/docker-compose.yml --env-file deploy/.env stop mysql
# 2) 观察影响：后端接口应报错/超时，前端静态页仍可打开
curl -sS -m 5 -o /dev/null -w 'health=%{http_code}\n' http://127.0.0.1/health
docker compose -f deploy/docker-compose.yml --env-file deploy/.env ps
# 3) 恢复
docker compose -f deploy/docker-compose.yml --env-file deploy/.env start mysql
docker inspect --format '{{.Name}} -> {{.State.Health.Status}}' moa-mysql
# 4) 验证
curl -sS http://127.0.0.1/health; echo
docker compose -f deploy/docker-compose.yml --env-file deploy/.env ps
# 5) 记录实测恢复耗时（本演练的实测值才可作为 RTO 结论）
```

#### 演练二：误删数据与备份恢复

```bash
# 1) 备份当前状态（演练基线）
TS=$(date +%Y%m%d_%H%M%S)
docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql \
  sh -lc 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --databases medical_ops' \
  > "backup/mysql/drill_${TS}.sql"
ls -lh backup/mysql/drill_${TS}.sql

# 2) 模拟误删（示例：删维表数据，演练环境执行）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql sh -lc \
  'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "DELETE FROM medical_ops.dim_department WHERE dept_code=\"EK\";"'

# 3) 停写并按 8.3.3 恢复
docker compose -f deploy/docker-compose.yml --env-file deploy/.env stop backend
docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql \
  sh -lc 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4' < "backup/mysql/drill_${TS}.sql"

# 4) 核对基线（dim_department 应恢复为 10 行）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql sh -lc \
  'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SELECT COUNT(*) FROM medical_ops.dim_department;"'
docker compose -f deploy/docker-compose.yml --env-file deploy/.env start backend
```

#### 演练三：卷级灾难恢复（模拟宿主磁盘损坏）

```bash
# 1) 备份卷（详见 8.3.4）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env stop mysql
docker run --rm -v deploy_mysql_data:/src:ro -v "$PWD/backup/volume:/backup" alpine \
  sh -lc 'cd /src && tar czf /backup/mysql_data_drill.tar.gz .'
ls -lh backup/volume/mysql_data_drill.tar.gz

# 2) 模拟卷丢失（演练环境）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env down -v

# 3) 重建编排并从快照恢复
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d
docker compose -f deploy/docker-compose.yml --env-file deploy/.env stop mysql
docker run --rm -v deploy_mysql_data:/dst -v "$PWD/backup/volume:/backup" alpine \
  sh -lc 'rm -rf /dst/* && cd /dst && tar xzf /backup/mysql_data_drill.tar.gz'
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d
```

#### 演练四：全站不可用（编排重建）

```bash
# 1) 记录当前版本与备份位置
docker compose -f deploy/docker-compose.yml --env-file deploy/.env images
ls -lh backup/mysql backup/volume

# 2) 完全销毁（演练环境；保留卷以便对比，生产慎用 -v）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env down

# 3) 从零重建
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d --build
# 4) 按 6.3~6.6 全量验证
curl -sS http://127.0.0.1/health; echo
curl -sS http://127.0.0.1/api/v1/ping; echo
```

### 13.2 多阶段镜像构建说明

两个 Dockerfile 的**构建上下文都是项目根目录**（compose 中 `context: ..`、`dockerfile: deploy/Dockerfile.*`），因此 `COPY` 源路径以 `backend/`、`frontend/`、`deploy/`、`data/` 开头；**构建命令必须在项目根执行，不要 `cd deploy`**。

#### 13.2.1 `Dockerfile.backend`（builder → runtime）

| 阶段 | 关键步骤 | 作用 |
| --- | --- | --- |
| `builder`（`python:3.11-slim AS builder`） | `WORKDIR /build` → `apt-get install build-essential` → `COPY backend/requirements.txt` → `python -m venv /opt/venv` → `/opt/venv/bin/pip install -r requirements.txt` | 依赖编译所需的编译链只装在这一层；`PIP_INDEX_URL` 已指向清华源；**先拷依赖清单再装依赖**，命中 layer 缓存可显著加速重建 |
| `runtime`（`python:3.11-slim AS runtime`） | `apt-get install curl tzdata` 并写 `TZ=Asia/Shanghai` → `groupadd --system app` + `useradd --system --gid app --home /app app` → `COPY --from=builder /opt/venv /opt/venv` → `COPY --chown=app:app backend/ data/ deploy/` → `RUN mkdir -p /app/uploads /app/backend/etl/logs` → `USER app` | **运行层不含编译工具**；虚拟环境由 builder **整目录复制**，运行层无需联网装 Python 依赖；容器以**非 root** 用户 `app` 运行；`WORKDIR /app/backend` 使 `etl` 与 `app` 两个包可直接按模块名导入 |
| 运行配置 | `ENV PATH="/opt/venv/bin:$PATH"`、`EXPOSE 8000`、`HEALTHCHECK --interval=30s --timeout=5s --start-period=25s --retries=3 CMD curl -fsS http://127.0.0.1:8000/health \|\| exit 1`、`CMD ["uvicorn","app.main:app","--host","0.0.0.0","--port","8000","--workers","2","--proxy-headers"]` | 健康探针 `curl /health` 与宿主机/编排健康状态一致；`--proxy-headers` 让后端信任 Nginx 传来的 `X-Forwarded-*` |

#### 13.2.2 `Dockerfile.frontend`（build → runtime）

| 阶段 | 关键步骤 | 作用 |
| --- | --- | --- |
| `build`（`node:20-alpine AS build`） | `WORKDIR /app` → `ENV NODE_ENV=production` → `COPY frontend/package.json frontend/package-lock.json* ./` → `npm config set registry https://registry.npmmirror.com` + `npm ci \|\| npm install` → `COPY frontend/ ./` → `npm run build` | 先依赖后源码以命中缓存；缺 `package-lock.json` 时自动降级 `npm install`；产物在 `/app/dist` |
| `runtime`（`nginx:1.27-alpine AS runtime`） | 写 `TZ=Asia/Shanghai` → `COPY --from=build /app/dist /usr/share/nginx/html` → `COPY deploy/nginx.frontend.conf /etc/nginx/conf.d/default.conf` → `EXPOSE 80` → `HEALTHCHECK ... wget -q --spider http://127.0.0.1/ \|\| exit 1` → `CMD ["nginx","-g","daemon off;"]` | 运行层只含 Nginx + 静态产物，无 Node 运行时；站点配置**打进行镜像**（与边缘 Nginx 用卷挂载不同） |

> **注意**：`Dockerfile.frontend` 内置的 `HEALTHCHECK` 探的是 `/`（由 `nginx.frontend.conf` 的 `try_files` 返回 `index.html`）；而 compose 里 `frontend` 服务的 `healthcheck.test` 覆盖为 `wget -q --spider http://127.0.0.1/healthz`（返回 `200 ok` 的轻量探针），**两者都可用**，以 compose 生效值为准。
>
> ⚠️ **待目标环境执行验证**：本节两个镜像的构建耗时、产物体积与构建日志均**未在本机实测**（本机无 Docker）。构建命令与失败常见点见 6.1 与 13.8。

### 13.3 数据库首次初始化（`sql/00_init_all.sql`）

**挂载变化（与 3.2、5.2 不同，以本节为准）**：compose 现在是 `../sql:/docker-entrypoint-initdb.d:ro`——把 `sql/` **整目录**挂到初始化目录**顶层**，而不是挂成子目录 `initdb.d/sql`。因此 `sql/00_init_all.sql` 会被官方镜像**自动执行**。

**只执行顶层文件的原因**：官方 `mysql:8.0` 镜像只在首次启动（数据目录为空）时，依次执行 `/docker-entrypoint-initdb.d/` **顶层的** `*.sql`、`*.sh`、`*.sql.gz`，**不会递归子目录**。项目各分层脚本都在子目录里（`dim/ods/dwd/dws/ads/optimize`），所以由 `00_init_all.sql` 作**唯一入口**，用 `SOURCE` 逐个加载。

**`00_init_all.sql` 的执行顺序**

| 步 | 语句 / 脚本 | 内容 |
| --- | --- | --- |
| 1 | `SOURCE /docker-entrypoint-initdb.d/dim/dim_tables.sql` | 公共维表 DDL + 初始化（科室、病种、费别、号别、DRG、日期维） |
| 2 | `SOURCE .../ods/ods_tables.sql` | ODS 贴源层建表 |
| 3 | `SOURCE .../dwd/dwd_tables.sql` | DWD 明细层建表 |
| 4 | `SOURCE .../dws/dws_tables.sql` | DWS 汇总层建表 |
| 5 | `SOURCE .../ads/ads_tables.sql` | ADS 集市层建表 |
| 6 | `SOURCE .../optimize/optimize_indexes.sql` | 幂等索引补建（存储过程判存在后创建，可重复执行，见 13.7） |
| 7 | `SOURCE .../dim/init_dict.sql` | 字典与**初始账号**（`sys_user`：`admin`/管理员、`analyst01`/运营分析师、`dept_hn`/科室用户 `HN`，`bcrypt` 哈希；全部 `INSERT ... ON DUPLICATE KEY UPDATE`，幂等） |
| 8 | `SELECT '数据库初始化完成：dim/ods/dwd/dws/ads 五层 + 索引 + 初始账号'` | 完成标记（日志中出现该行即代表全部脚本走完） |

> **注意**
> 1. `SOURCE` 使用的是**容器内绝对路径** `/docker-entrypoint-initdb.d/...`，因此不要再改挂载点，否则 `SOURCE` 全部失败但容器仍会"启动成功"（只报 `ERROR`，不影响进程起）。
> 2. **初始化只跑一次**：仅当 `mysql_data` 卷为空时触发。卷已有数据后再新增脚本、或 `docker compose restart`，都不会执行；需要重跑见 13.8 Q2。
> 3. 依赖 `MYSQL_DATABASE`（默认 `medical_ops`）与账号口令环境变量，须先完成 4.3 的 `deploy/.env`。

| 命令 | 用途 | 判读要点 |

| `docker exec ... /health`、`/healthz` | 绕过边缘 Nginx 直测容器自身 | 排 502/404 时用来区分"容器内服务坏了"还是"反代链路坏了" |

### 13.5 健康检查脚本说明（`deploy/health_check.py`）

脚本仅用 Python 标准库（`argparse` / `json` / `subprocess` / `urllib`），**无需安装任何依赖**，可在宿主机或容器内运行。

**服务清单常量（`SERVICES`）**

| 服务键 | 容器名 | HTTP 探针 |
| --- | --- | --- |
| `mysql` | `moa-mysql` | 无（`None` → 记为"无 HTTP 探针"且视为通过） |
| `backend` | `moa-backend` | `http://127.0.0.1:8000/health` |
| `frontend` | `moa-frontend` | `http://127.0.0.1:4173/` |
| `nginx` | `moa-nginx` | `http://127.0.0.1/health` |
| （链路） | — | `/api` 反代探针：`http://127.0.0.1/api/ping` |

**`check_service_health(service_name, *, skip_docker=False)` 判定逻辑**

| 判定项 | 计算方式 | 说明 |
| --- | --- | --- |
| `docker_ok` | `subprocess.run(["docker","inspect","--format","{{json .State}}",容器])` → 解析后要求 `State.Running == True` **且** `State.Health.Status ∈ {healthy, none}` | 容器不存在时返回 `false` 并带 `stderr` 前 120 字；`docker` 命令不存在时返回 `docker 不可用：FileNotFoundError` |
| `http_ok` | `urllib` 请求该服务的 HTTP 探针，状态码 **2xx/3xx** 视为通过；无探针的服务记为通过 | 超时 5 秒；连接失败/超时记为 `连接失败：<异常类型>` |
| `healthy` | `skip_docker=True` 时 **只看** `http_ok`；否则要求 `docker_ok and http_ok` | 返回值字典字段：`service`、`container`、`docker_ok`、`docker_detail`、`http_ok`、`http_detail`、`healthy` |

**`check_all(*, skip_docker=False)` 判定逻辑**

1. 对 `SERVICES` 中四个服务逐个调用 `check_service_health`；
2. 追加执行 `/api` 反代探针 `http://127.0.0.1/api/ping`（该请求依次经过 `moa-nginx` → `moa-backend`，因此**同时验证了 Nginx 与后端的连通性**）；
3. `all_healthy = 四个服务全部 healthy and api_ok`；
4. `main()` 打印表格式汇总，并以退出码表达结论：**`0` = 全部健康，`1` = 存在异常**。

**预期输出形态（示意，待目标环境验证）**

```
服务        容器            容器状态                HTTP 探针          结论
mysql      moa-mysql       running=True health=healthy 无 HTTP 探针      ✅ 健康
backend    moa-backend     running=True health=healthy HTTP 200          ✅ 健康
frontend   moa-frontend    running=True health=healthy HTTP 200          ✅ 健康
nginx      moa-nginx       running=True health=healthy HTTP 200          ✅ 健康

/api 反代链路：http://127.0.0.1/api/ping → HTTP 200 ✅

总体结论：✅ 四服务与反代链路均健康
```

> **注意（`frontend` 探针的适用范围）**：脚本里 `frontend` 的 HTTP 探针是 `http://127.0.0.1:4173/`，这是**本地 `npm run preview` 预览端口**；容器化部署时 `frontend` 只有 `expose 80`、**没有发布宿主机端口**，因此在目标服务器上该项探针必然失败，`all_healthy` 会判为 `false`。此时请：① 以 `docker compose ps` 的 `Up (healthy)` 判定 frontend 容器状态（其 compose 健康检查探的是容器内 `/healthz`）；② 用 `python deploy/health_check.py --service nginx` 验证对外入口与 `/api` 链路是否真正可用。
>
> **注意（不要在无 Docker 的机器上指望"自动降级"）**：脚本在 `docker` 命令不存在时**不会自动**切换为纯 HTTP 模式，而是把 `docker_ok` 记为 `false`（明细为 `docker 不可用：FileNotFoundError`）。本地预览场景请显式加 `--skip-docker`。

### 13.7 查询优化与回刷

#### 13.7.1 索引优化（`sql/optimize/optimize_indexes.sql`）

- **幂等实现**：脚本先 `DROP PROCEDURE IF EXISTS sp_add_index_if_missing` 再重建存储过程 `sp_add_index_if_missing(p_table, p_index, p_columns)`；过程内查 `information_schema.statistics` 判断索引是否已存在，不存在才 `PREPARE`/`EXECUTE` 一条 `ALTER TABLE ... ADD INDEX`，存在则输出 `[SKIP]`，**可反复执行**。
- **索引清单**：

| 层级 | 表 | 索引（列） |
| --- | --- | --- |
| ADS 指标结果 | `ads_indicator_result` | `idx_metric_dim_gran_date(metric_code, dim_value, granularity, stat_date)`、`idx_dim_date(dim_value, stat_date)`、`idx_status(data_status, metric_code)` |
| DWS 汇总 | `dws_dept_daily` | `idx_dept_date(dept_code, stat_date)`、`idx_stat_date(stat_date)` |
| 主题集市（8 张） | `ads_outpatient_theme`、`ads_inpatient_theme`、`ads_income_theme`、`ads_drug_theme`、`ads_consumable_theme`、`ads_drg_theme`、`ads_efficiency_theme`、`ads_service_theme` | 各补 `idx_dept(dept_code)` |
| DWD 明细 | `dwd_visit_detail`、`dwd_charge_detail`、`dwd_inpatient_visit_detail` | `idx_type_date(visit_type, visit_date)`、`idx_dept_date(dept_code, visit_date)`、`idx_class_date(fee_class, fee_date)`、`idx_dept_discharge(dept_code, discharge_date)` |
| 维表 | `dim_department`、`dim_date` | `idx_parent(parent_code)`、`idx_ym(year_month)`、`idx_stat_period(in_stat_period, date_value)` |

- **分区改造说明**：脚本末尾以**注释形式**给出 DWS/ADS 事实表按月 `PARTITION BY RANGE (TO_DAYS(stat_date))` 的 `ALTER TABLE` 示例。原因：MySQL 要求**分区键必须包含在主键中**，且演示库每表仅 910～3,000 行，拆分区无收益；生产环境（数据保留 2 年、按季/月增长）再按注释启用。
- **执行与验证**：该脚本已作为 `sql/00_init_all.sql` 的第 6 步在首次初始化时执行；单独重跑时在容器内以 root 执行即可（可重复）。脚本自带三条验证输出：① 索引清单（`information_schema.statistics` 聚合列）；② `EXPLAIN` 指标查询，期望命中 `idx_metric_dim_gran_date` 且 `type=range`；③ 可选清理 `DROP PROCEDURE sp_add_index_if_missing`。
- **慢查询定位**：compose 已固化 `--slow_query_log=1 --long_query_time=1`，超过 1 秒的语句会进慢日志，可按 8.1 的方式在容器内查看。

```bash
# 单独重跑索引优化（可重复执行）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec -T mysql sh -lc \
  'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 medical_ops' \
  < sql/optimize/optimize_indexes.sql
```

#### 13.7.2 区间回刷（`python -m etl.jobs.backfill`）

| 项 | 说明 |
| --- | --- |
| 用法 | `python -m etl.jobs.backfill <start> <end>`（**位置参数**，先开始日期后结束日期，格式 `YYYY-MM-DD`；省略则取 `STAT_PERIOD`，即 `2025-04-01` ~ `2025-06-30`；批次日期取 `end`） |
| 重跑链路 | `run_clean_all`（DWD 清洗）→ `run_wide_tables`（DWD 宽表，按区间）→ `build_dws_daily` + `build_theme_marts`（DWS 与主题集市）→ `run_indicators`（ADS 指标，**同时产出 `month` 与 `period` 两套粒度**） |
| 幂等性 | 各层写入均**先按批次删除再插入**（打印日志即"先删后插，幂等"），可对同一区间反复重跑，不会造成数据翻倍 |
| 不动 ODS | 回刷只重跑**加工链路**，不重新抽取 ODS（ODS 是按源文件全量抽取的）；若源文件本身变了，先跑 `extract_ods` |
| 维表 | 默认不初始化维表；需要时传 `include_dim=True`（会先跑 `init_dim`） |
| 输出 | 打印各层行数与一行汇总，并返回含 `date_range`、`batch_date`、`dwd`、`dwd_wide`、`dws`、`ads`、`summary` 的字典 |
| 连接 | 通过 `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD` 环境变量拼 MySQL 连接串（compose 已注入后台容器）；**未设置 `DB_HOST`/`DB_URL` 时降级为 SQLite 开发库** `backend/etl/logs/moa_dev.db` |

```bash
# 2) 宿主机执行（需自行 export DB_HOST/DB_USER/DB_PASSWORD 等，或允许降级到 SQLite）
cd backend && python -m etl.jobs.backfill 2025-04-01 2025-06-30
```

### 13.8 常见问题补充（四服务形态）

**Q1：镜像构建/四服务启动没在本机验证过，能直接上生产吗？**
不能当"已验证"。本手册编制环境**未安装 Docker**，13.2、13.4 的构建与启动结论均为按配置推导。请在**目标环境**按 13.4 逐条执行并留存 `docker compose ps` 与 `python deploy/health_check.py` 的输出后，再纳入验收记录；构建失败常见点见 6.1。

**Q2：`00_init_all.sql` 改了/新增脚本，为什么重启容器没生效？**
MySQL 初始化**只在 `mysql_data` 卷为空的首次启动执行一次**。卷已有数据时：① 新增或修改脚本不会自动执行，需手工执行（`docker compose ... exec -T mysql ... < 脚本`，见 5.2）；② 确需整库重建时，`docker compose -f deploy/docker-compose.yml --env-file deploy/.env down -v` 会**删除** `mysql_data`（连同数据），随后 `up -d` 才会重新初始化——**生产环境执行前必须先备份**（8.3）。

**Q3：直接访问 `http://<IP>/dashboard` 或刷新页面报 404？**
SPA 的 history 路由依赖 `frontend` 容器的 `try_files $uri $uri/ /index.html` 回退。出现 404 时按序排查：① 请求是否真的到了边缘 Nginx（`docker exec moa-nginx tail -n 50 /var/log/nginx/moa.access.log`）；② `upstream moa_frontend` 是否指向 `frontend:80` 且容器在跑；③ `frontend` 的 `default.conf` 是否被覆盖（`docker exec moa-frontend cat /etc/nginx/conf.d/default.conf` 应含 `try_files`）；④ 若 `/assets/*` 也 404，说明 `dist` 未打进镜像（检查 6.1 构建日志中的 `npm run build`）。

**Q4：页面能打开但接口报 502 Bad Gateway？**
502 表示边缘 Nginx 连不上/等不到后端：① `docker compose ps` 看 `moa-backend` 是否 `Up (healthy)`（`backend` 依赖 `mysql` 健康，MySQL 未 healthy 时后端起不来）；② `docker exec moa-backend curl -fsS http://127.0.0.1:8000/health` 直测容器内服务；③ 看 Nginx 错误日志 `moa.error.log`（`connect() failed` 多为后端未就绪，`upstream timed out` 看是否踩到 60s/180s 超时）；④ 只有 `/api/llm/*` 慢或 502，属大模型调用耗时，确认 `LLM_*` 配置与 180s 超时（10.2、9.8）。

**Q5：`docker compose ps` 显示 `unhealthy` 怎么定位？**
先用 `docker inspect --format '{{json .State.Health}}' moa-backend`（或 `moa-mysql` / `moa-frontend` / `moa-nginx`）看 `Log` 里最后一次失败的探针输出：① `mysql` → `mysqladmin ping` 失败，多为口令与 `.env` 不一致（9.3）；② `backend` → `curl /health` 失败，看 `docker compose logs backend`（末行常为数据库连接异常）；③ `frontend` → `wget /healthz` 失败，多为容器内 Nginx 未起来或配置语法错（`docker exec moa-frontend nginx -t`）；④ `nginx` → `wget /health` 失败，通常是后端不可用导致 `/health` 反代不通，先修后端。

**Q6：回刷跑完了，看板数值怎么还是旧的？**
按序检查：① **粒度**——回刷同时产出 `month` 与 `period` 两套粒度，若页面选的是"月度"而只核对过"全期"，两者本就不等（3.1、15.2）；② **缓存**——看板数据缓存 5 分钟，等 5 分钟或点「刷新」（3.3）；③ **统计期**是否覆盖回刷区间（回刷 `2025-05-01~2025-05-31` 不会改变 4 月数据）；④ 确认回刷真的写入了目标库——宿主机直跑时若未设置 `DB_HOST`，会降级写进 `backend/etl/logs/moa_dev.db`（SQLite），容器里的 MySQL 自然看不到变化。

**Q7：`health_check.py` 里 `frontend` 一直失败？**
该探针固定指向 `http://127.0.0.1:4173/`（`npm run preview` 预览端口），容器部署时 `frontend` 不发布宿主端口，故必失败——用 `docker compose ps` 的健康状态与 `--service nginx` 的 `/api` 链路结果判定即可（详见 13.5 的两条注意）。

**Q8：宿主机或其他机器连不上 3306？**
当前 compose 为 `127.0.0.1:3306:3306`，**只允许宿主机回环访问**，属安全收敛后的预期行为（与 2.4 旧描述不同）。容器间通信用 `mysql:3306`；DBA 需要远程连库时走 SSH 隧道或跳板机，不要为此把映射改回 `0.0.0.0`（10.3）。
