### 1.2 阶段划分原则

项目不是按"技术栈"横向切分（前端一组、后端一组各干各的），而是按**数据链路 + 应用链路双链切分**：前半程沿数据链路自下而上单向收敛，后半程沿应用链路自上而下逐层交付。

```
数据链路（阶段二 → 阶段三，自下而上、逐层收敛）
  源文件/源库 → ODS 贴源 → DWD 明细 → DWS 汇总 → ADS 指标结果
  特点：每层输入输出确定，层间有质量门禁，指标口径只在 ADS 实现一次

应用链路（阶段四 → 阶段五 → 阶段六，自上而下、逐层交付）
  ADS 结果 → 后端接口 → 前端看板/报表 → 大模型智能分析
  特点：每层只消费下一层的既成事实，不做二次计算
```

选择该划分方式的五条理由：

1. **医疗数据必须先保证"数对"，再讨论"好用"**。若先做看板，前端会在错误口径上放大错误，且返工成本随层数成倍上升；把 ODS/DWD/DWS/ADS 放在阶段二、三，优先锁定口径与数据质量，后续阶段只做"取数"。
2. **口径唯一性需要物理保证**。指标只在 ADS 层实现一次（《概要设计》ADR-01），接口与前端只取数不计算，这条约束只有在"数仓阶段先于服务与前端阶段"时才可能被强制执行。
3. **每阶段可独立验收、可回滚**。按链路切分后，任一阶段失败只影响其下游，ODS 层可重跑、ADS 层可按 `etl_batch_id` 幂等重插，避免"整体关联合不上"的僵局。
4. **有限并行有明确接口面**。阶段四可在阶段三 ADS 表结构冻结后先行开发（用样例数据桩联调）；阶段五以阶段四的接口契约（OpenAPI）为输入；阶段六复用阶段三的 `metric_def` 口径库与阶段四的鉴权与数据范围，避免重复造轮子。
5. **与技术分层一一对应**。7 个阶段自然映射《概要设计》的"计算层 / 服务层 / 展示层"与"两侧支撑"（安全与可观测），便于把架构约束落实到具体任务上。

        ▼

        ▼
阶段五 前端可视化开发         [FE 主责]
  图表组件库(12 类) → 3 套看板 → 8 个分析页面与多维报表
        │
        ▼

  测试执行与缺陷闭环 → 容器化部署与验收总结 → 验收结论与上线

**关键约束**：服务层只读 ADS/DWS，不直接访问 ODS（《概要设计》5.1）；DWS 只做聚合，指标口径只在 ADS 实现；前端与 AI 不得二次计算指标（《指标口径手册》1.2 唯一口径原则）。

### 2.3 阶段任务数校验（23 项描述 → 20 项单元任务）

任务书给出的阶段任务描述共 3+4+4+3+3+3+3 = **23 项**。为满足"7 个阶段、共 20 项单元任务"的硬性要求，在**不增加、不删除任何阶段名与工作内容**的前提下，对 3 组强关联工作做了合并（合并后子活动仍全部保留在任务技术要点中）：

| 合并编号 | 合并前（任务书描述） | 合并后任务 | 合并理由 |
| --- | --- | --- | --- |
| M-1 | 工程骨架搭建 ＋ 开发环境与规范 | T02 工程骨架与环境规范搭建 | 二者同属"工程初始化"，一次交付、一次评审，拆分会导致同一批配置被评审两遍 |
| M-2 | 指标口径定义 ＋ 指标计算与校验 | T09 指标口径定义与指标计算校验 | 口径定义（`metric_def` + 手册）与计算校验（SQL + 断言）是同一条流水线的两步，且校验以口径为断言基准，必须同人同阶段闭环 |
| M-3 | 容器化部署 ＋ 验收与项目总结 | T20 容器化部署与验收总结 | 部署是验收的前置条件，验收结论依赖容器化环境的验收测试结果，合并后里程碑 M7 唯一、结论唯一 |

**校验算式**

```
阶段一 2 + 阶段二 4 + 阶段三 3 + 阶段四 3 + 阶段五 3 + 阶段六 3 + 阶段七 2 = 20
任务书 23 项 − 合并 3 次（每次减 1） = 20 项  ✔
编号连续性：T01…T20 共 20 个编号，无跳号、无重号  ✔
```

### 3.6 阶段六：智能分析与大模型对接

## 六、质量管理

### 6.1 代码评审流程

```
提交前自检（本地构建/测试通过、无调试残留、无硬编码密钥）
   ↓
发起合并请求（feature → develop），填写：任务号、变更点、影响面、自测结论
   ↓
CI 门禁：依赖安装 → 静态检查 → 单元测试 → 构建成功（任一失败则打回）
   ↓
同行评审 ≥ 1 人（跨角色：数据改动由 BE 或 QA 复审，接口改动由 FE 复审）
   ↓
评审意见处理（必改项修完并回复 → 重新评审）
   ↓
PM/阶段负责人审批 → 合并 → 删除特性分支
```

**评审清单（必查项）**

| 维度 | 检查点 |
| --- | --- |
| 口径一致性 | 指标数值是否来自 ADS/`metric_def`；有无前端或接口层二次计算；登记/流水/财务三口径是否按手册取数；`metric_version` 是否传递 |
| SQL 安全 | 仅访问 `ads_*`/`dws_*`/`dim_*`；只读；参数化（无字符串拼接）；无查询期多表大聚合；有 `limit` |
| 权限 | 数据范围是否由依赖注入统一追加；有无手写 `dept_code` 过滤；越权是否返回 40302；导出是否二次鉴权 |
| 响应规范 | 统一响应包 `code/message/data/trace_id`；错误码使用手册表；异常不外泄堆栈 |
| 脱敏与隐私 | `patient_name/id_card/phone` 是否只出现在 ODS/DWD 合规位置；日志与告警正文不含隐私字段 |
| 可观测 | 关键路径有日志、有 `trace_id`、批次号/`calc_batch_id` 可追溯 |
| 命名与结构 | 表名前缀、文件命名、目录归属、函数职责单一（第 7.2 节） |
| 测试 | 新增逻辑有对应测试；口径相关改动补断言用例；无注释掉的断言 |
| 依赖与配置 | 新增依赖须写入 `requirements.txt`/`package.json` 并锁版本；敏感配置走环境变量 |
| 文档同步 | 表结构/接口/口径变更须同步更新《详细设计》或《指标口径手册》 |

**红线（命中即打回，不做讨论）**：硬编码密钥；`DROP/TRUNCATE/DELETE` 无 `WHERE` 或越权写操作；前端对指标二次计算；隐私字段进入日志或出网；口径与手册不一致。

## 七、配置与变更管理

### 7.1 Git 分支模型

采用轻量 Git Flow（适合小团队 + 阶段交付）：

| 分支 | 用途 | 生命周期 | 保护策略 |
| --- | --- | --- | --- |
| `main` | 可交付、可演示的稳定版本；每个里程碑打 tag（`v0.1-m1` … `v1.0`） | 永久 | 禁止直推，仅接受 `release/*`、`hotfix/*` 合并 |
| `develop` | 集成主线，阶段内日常集成 | 永久 | 禁止直推，仅接受 `feature/*`、`fix/*` 合并 |
| `feature/T{NN}-{短名}` | 单任务开发（如 `feature/T09-metric-calc`） | 任务期间 | 与任务号一一对应，合并后删除 |
| `fix/{缺陷号}-{短名}` | 缺陷修复（如 `fix/S2-013-export-pdf`） | 修复期间 | 关联缺陷编号 |
| `release/v{x.y}` | 里程碑前封版与回归 | 至里程碑结束 | 只允许缺陷修复，不允许新增功能 |
| `hotfix/{问题}` | 验收后紧急修复 | 短 | 同时合入 `main` 与 `develop` |

**提交信息规范**：`type(scope): 摘要 (#T{NN} 或 #S{级}-{号})`
`type` ∈ `feat|fix|docs|test|refactor|chore|style|perf`；`scope` ∈ `etl|dws|ads|api|web|ai|deploy|docs`。
示例：`feat(ads): 实现 M11 床位使用率指标计算 (#T09)`、`docs(流程): 补充阶段七验收步骤 (#T20)`。

**合并规则**：至少 1 名 reviewer 通过 + CI 通过 + 无冲突 + 关联任务号或缺陷号；禁止 `--force` 推送到 `main`/`develop`。

### 7.3 指标口径变更流程

口径变更严格按《[指标口径手册](指标口径手册.md)》第 9 章执行，本流程为落地版：

```
① 需求提出（业务侧/测试侧，填写变更申请：指标编号、原口径、新口径、理由、期望生效期）
        ↓
② 数据组评估（是否影响公式/来源表/ADS 表结构/历史数据；影响 M 列表与下游看板清单；
              是否需重跑与回刷；工期与风险等级）
        ↓
③ 评审通过（PM + DE + BE + FE + QA；S1 级口径变更需指导老师复核）
        ↓
④ 更新基线（同步修改《指标口径手册》第 4/5 章 + `metric_def` 元数据 + 断言用例）
        ↓
⑤ 重跑与回刷（按 `calc_batch_id` 幂等重算，`metric_version` 升版，新旧版本并行一个统计周期）
        ↓
⑥ 通知使用方（看板/报表/问数侧；前端通过接口 `version` 参数指定生效版本）
        ↓
⑦ 归档（变更记录进《指标口径手册》第 9 章变更表；评审纪要入过程档案）
```

### 8.4 上线与回滚

**上线前检查清单**

| 项 | 检查内容 |
| --- | --- |
| 配置 | `deploy/.env` 中数据库口令、`JWT_SECRET`、`LLM_API_KEY` 已改为生产值，且未入库入仓 |
| 账号 | 三个默认账号密码已修改或已明确禁用计划 |
| 镜像 | 镜像 tag 固定（禁止 `latest`），保留上一版本镜像 |
| 数据 | MySQL 数据卷已做一次全量快照备份（`mysql_data` 卷或 `mysqldump`） |
| 端口 | 80 对外；8000 仅容器内 `expose`；3306 是否对外需明确决策 |
| 健康 | `/health` 正常；三容器 restart 策略为 `unless-stopped` |
| 文档 | 《部署运维手册》与本次部署实际步骤一致 |
| 观察 | 上线后 24 h 内监控接口错误率、慢查询、容器重启次数 |

**回滚触发条件**：核心功能不可用且 15 分钟内无法定位；指标结果出现口径性错误；出现隐私泄露或越权；容器反复重启（≥3 次/小时）。

**回滚步骤**

```
① 停止流量（Nginx 层切换到维护页或上游摘除）
② 回退镜像：将 backend/frontend 镜像 tag 指向上一个已验证版本，docker compose up -d
③ 回退数据（仅当本次上线含表结构或数据变更）：
   停止 backend → 恢复 mysql_data 快照或按备份 dump 恢复 → 校验 6 张 ODS 行数与 ADS 关键指标
④ 重启并验证：三容器 healthy → /health → 登录 → 抽查 5 项指标
⑤ 记录：回滚原因、时间、版本、影响范围、后续整改项（写入运维记录与缺陷清单）
```

**数据回滚原则**：数仓加工遵循"按 `etl_batch_id` / `calc_batch_id` 幂等重插"，优先"重跑恢复"而非"整库回档"；整库回档需 PM 与数据负责人双签。
